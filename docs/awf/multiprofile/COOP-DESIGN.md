## 2. Revision and guard model (slice 2 contract)

Use immutable records and nonnegative counters. Each committed record mutation increments exactly once; admission/CAS rejection increments nothing. Installing or clearing a durable reservation is itself a mutation, including when the business operation later aborts. Idempotent replay returns its original result without incrementing. New records start at 0, expected absence is `ABSENT`; missing accounts retain the current logical revision 0 convention. Use `Math.addExact`, never wrap. For identical FILE/Redis semantics cap all revisions/fences used by these new scripts at `2^53-1` until epoch comparison is made decimal-safe throughout the fabric: current Lua uses `tonumber` (`RedisProfileRepository.java:98–112`). Exhaustion refuses mutation and needs offline migration; it does not reset a counter.

| Counter / key | Advances for | Does not advance for |
| --- | --- | --- |
| Account `A(player)` | Accessible profile index and per-account aliases, slot limit, active profile, active membership epoch, login/session generation, operation reservation | Another member's snapshot or profile rename |
| Profile metadata `M(profile)` | Owner, roles, members/epochs, name, rules/type policy, lifecycle/hold, binding revision reference, membership reservation | Member save; bank or collection mutation |
| Shared state `S(profile)` | Shared bank, personal-bank subaccounts, collections, contributions, currency identity, reservations and transfer receipts | Rename, member capture |
| Member head `R(profile,player,membershipEpoch)` | Publishing that member's authoritative snapshot, initialization, source consumption or delivery | Other members' saves or metadata updates |

A membership epoch is a random UUID generated on admission and never reused. Removed streams remain forensic data, never an admissible login source. Profile heads map at most 64 current members to epochs; member heads are independent records so saving one member does not rewrite all metadata. `ProfileSnapshot.revision` means R for type 10, never M or S. Initialization is an explicit head state (`UNINITIALIZED`, `READY`, `CONSUMED`), not `aurora.snapshot.<UUID>` metadata. Exact lookup is `(profile, member, epoch, snapshotId)`; the head's ID, revision and checksum must match the selected snapshot. Older **or newer** mismatches fail closed. This replaces the current freshness coupling at `ProfileEngine.java:1345–1354,1722–1730` without relaxing stale detection.

Introduce `CoopWriteGuard`: operation UUID + payload digest; typed profile claim P; typed player/account claim Q where applicable; expected A/M/S/R/record revisions; expected membership epochs; expected active profile; reservation IDs. Explicit methods take only the guards they need, but none accept `ANY`, null required claims or unguarded default implementations. Claims bind resource kind, UUID, node, process incarnation, owner token, fence and expiry. Repository checks identity/role/status as well as the version vector. A client cannot attach an unrelated valid claim to an arbitrary profile write.

| Mutation | Required claim and commit-time comparisons |
| --- | --- |
| Create/account slots/name assignment | Q(actor/account), expected A; new profile P + M absent; account-local alias uniqueness inside the same reservation/transaction |
| Shared display-name, role/rule/hold/binding change | P(profile), Q(actor), expected actor A + M, current authorized role; binding has its own revision checked too |
| Account-local alias rename | Q(account), expected A, current membership; normalized alias uniqueness within this account; no M change |
| Save/init member stream | Q(member), expected A + M + R + epoch, active profile equality; M is compared but not incremented; ordinary save does not require P |
| Switch active account | Q(player), expected A; both profiles' M, membership epochs and exact R/IDs; use P only for metadata changes, not for ordinary independent member saves |
| Shared/bank mutation | P(profile), Q(actor), expected A + M + S; actor active on profile and allowed role; bank transfer also expects operation/receipt revision |
| Invite create/revoke; vote create/cast | P(profile), Q(actor), expected A + M + invite/vote revision (or absence); current permission, epoch and expiry |
| Accept / remove member | P(profile), Q(actor) and Q(affected account), expected affected A + M + invite/vote + affected R; ordered reservation protocol below |
| Salvage prepare / delivery | P(profile), Q(claimant), expected claimant A + M + R + salvage revision; source epoch/head consumed and removal transaction committed |
| Journal transition/receipt/cleanup | Required P/Q for affected resource, expected intent revision + immutable operation digest; cleanup also checks pins and terminal status |

Q(actor) is a short account mutation claim for an offline administrator or an online player session claim. An online target's Q cannot be stolen for kick/removal: first gate/disconnect it and finish its save, then release Q, or leave the operation pending until that node responds/lease expires. All multi-claim acquisitions sort by `(kind, UUID)`; on refusal release only newly acquired claims, retain durable intent, and retry through bounded admission. Never wait for another claim while holding an entity thread or I/O queue slot.

**FILE enforcement:** retain the OS directory lock. Add one repository/coordinator commit lock, shared with local claim validation/release, so claims cannot expire/take over between validation and publication. Check monotonic expiry inside that lock immediately before logical commit. Check the full expected vector under it. File writes outside that lock may only stage immutable blobs. File CAS alone remains single-process; distributed+FILE stays refused (`ProfileRuntime.java:142–168`).

**Redis enforcement:** add multi-key scripts checking *all* P/Q leases using Redis TIME, resource identity, exact incarnation/token/fence, revisions, reservation ownership, roles, active profile and epoch before any mutation. Return `FENCED` for authority failure and `STALE` for revision/predicate drift, preserving current error mapping (`RedisProfileRepository.java:826–853`). Validate all staged data and types before first write: a Lua runtime error does not roll back earlier Redis commands. Keep existing single-primary/no-cluster restriction. Both repositories expose concrete `prepareIntent`, `commitIntent`, `intentStatus`, `publishMemberSnapshot`, `mutateShared`, and paged-list operations; no Redis no-op stubs.

## 3. Ownership and online members

Decision: separate **Q(player)** (one online session across every profile/node) from **P(profile)** (short exclusive metadata/shared-state transaction authority). P is not a lifetime player session. Ordinary member saves use Q and membership-version checks. Profile-wide changes acquire P; shared mutations from different nodes serialize through P and S CAS. P is released after the transaction becomes durable/recoverable; changing players does not automatically transfer it. Each node keeps local references to an acquired P for its operation only; concurrent members never replace one another's token. Quit releases that player's Q only, not another member's P. Maintain separate claim maps and heartbeats; remove the assumption in `ProfileEngine.java:442–458,558–591` that profile owner equals active player.

Same-node members can simultaneously capture/play/save distinct streams. Cross-node members can simultaneously hold distinct Q claims and save distinct streams in Redis; either node may acquire P for a bounded metadata/shared mutation. New P and Q namespaces must be disjoint (`coop:profile-claim:<id>` and `coop:player-claim:<id>`), not raw UUIDs in the existing profile session namespace. Extend the fabric claim mechanism with strict “same owner token renews; different token refuses while live” semantics, including on the same node. Do not reuse local same-node supersession (`LocalProfileOwnership.java:58–67`) or assume `RedisProfileOwnership`'s current profile-keyed SessionFabric already implements Q.

A new/reconnected player obtains a fresh session generation under Q and increments A before capture or restore admission. A token is never reused after quit. Local provider incarnations continue to invalidate comparison with prior-process fences (`ProfileTransition.java:15–19`); Redis epochs must remain monotonic in the supported primary history. Redis failover that rolls epochs/data back remains unsupported (`RedisProfileRepository.java:60–68`).

On confirmed Q loss, freeze affected player, reject captures/mutations, cancel queued apply using a generation token, and disconnect through its entity scheduler if authority cannot be recovered. Do not reacquire and publish an old capture. On uncertain renewal, block durable mutations and new gameplay admission until validated; never call a timeout proof of expiry. On P loss, stop the operation, leave its intent/reservation for recovery, and do not write compensation with the stale token. Other members' independent saves may proceed unless a membership reservation covers them. Renew every operation-held claim, including recovery; shutdown cancels admission, gates players, drains bounded work, retains unresolved intents, then releases exact claims and closes storage (`ProfileRuntime.java:249–263,336–373`; `ProfileEngine.java:716–798,1873–1887`).

**OWNER DECISION OD-1 — cross-node world access:** options: (a) route all members using one bound AWF world to its authoritative host, while allowing co-op metadata/member storage across nodes; (b) restrict all co-op sessions to one node initially; (c) design multi-writer world replication separately. Recommendation (a), fail closed for unavailable routing; (b) is an acceptable first rollout. This proposal does not authorize loading the same world independently on two nodes. Current world preparation/return paths are `ProfileEngine.java:655–706,1332–1343`; routing/live-state handoff remains an open gate (`docs/releases/BUILD-50-READINESS.md:76–77`). The transport and external SSB routing support are unknown here. Until OD-1 is resolved, reject cross-node gameplay activation requiring the same bound world; do not silently pretend storage CAS solves world ownership.

*Build 56 (2026-11-04, owner decision):* (b) shipped as Builds 53–55.1. Build 56 adds a per-node role behind `coop.cross-node` (default off): a **satellite** node (`coop.world-host: false`, no bound worlds, switching off) takes no node claim and is never refused `WRONG_NODE`; a **world host** keeps OD-1 against other world hosts. Storage CAS is not asked to solve world ownership: the node claim still marks the one node that hosts the bound world, and a satellite never touches it. See [DISTRIBUTED-OWNERSHIP.md](DISTRIBUTED-OWNERSHIP.md#co-op-across-nodes-build-56-coopcross-node).

## 4. Records, versioning and migration

Decision: retain AWFR framing structure (magic, format byte, type byte, revision long, payload length int, payload SHA-256) but introduce **format 2** for the complete co-op repository. Keep strict format-1 decoding only for offline import. Do not append an ignorable extension to a format-1 profile. New payloads start with unsigned-short schema version 1, use big-endian numeric fields, UUIDs as two longs, explicit stable numeric enum tags (not Java ordinals), bounded UTF-8 lengths, and reject duplicate keys/unknown required fields/trailing bytes. Header revision must equal payload revision where repeated. Exact future schema changes require new schema versions; unsupported schemas refuse writes, not lossy round-trips. Existing checksums cover payload, not headers: validate header identity/revision against decoded payload (`ProfileRecords.java:51–84`).

New member streams never fall back to old flat type-4 snapshots after migration. Current migration entry point is `ProfileRuntime.java:313–324`; extend `ProfileRepositoryMigration.java`, rather than bypassing startup repository selection.

**Downgrade decision:** unsupported against migrated data. A format-1 reader currently ignores profile trailing bytes, and its writer emits only old fields (`ProfileRecords.java:122–158`), so readable WIP extensions are not downgrade-safe. Format-2 records make old per-record reads fail. **OWNER DECISION OD-2 — deployment rollback gate:** choose (a) deployment tooling refuses pre-co-op binaries whenever the configured store is format 2, rollback only by restoring the complete pre-migration backup into an isolated store; or (b) backport a startup format gate into every allowed older binary first. Recommend (a); deployment-tool implementation/ownership is unknown and is an activation blocker. Per-record rejection is defense in depth, not a claim that PR #62 itself has a global gate. Never advertise a safe in-place downgrade or run old and new writers concurrently. No downgrade exporter is included in slices 2–7.

## 5. Recoverable transactions and journals

Current repository operations are recoverable, not multi-record atomic (`ProfileRepository.java:11–14`); current switch journals carry exact rollback references and two fences (`ProfileTransition.java:15–42`). Extend that discipline to all co-op records.

Decision: a common intent protocol with states `PREPARED → COMMITTED → FINALIZED`, or `PREPARED → ABORTED`; `RECOVERY_REQUIRED` records an unresolved outcome without implying rollback. Receipt lookup precedes any retry. Same operation ID plus different payload digest is INVALID_REQUEST. PREPARED contains full immutable proposed after-images and expected before-revisions, not merely “accept invite”. Reserve affected account/profile/head resources before exposing changes. New readers encountering a reservation resolve/help the intent or return RECOVERY_REQUIRED; they never read a partially published relationship as valid. Reservations remain durable after a claim lease expires; a new fence may recover them, not skip them. PREPARED stores both the pre-reservation version vector and the post-reservation vector: installing a reservation advances the containing record once; COMMIT compares the post-reservation vector and advances changed records once more. Abort clears its own reservations with another CAS increment. After-images are encoded with the final revisions, not the original read revisions. Repeated prepare/commit/abort is resolved by operation ID before revision checks, so replay does not increment again. Type-5 switch phases remain detailed player-apply progress; type-12 phases describe the durable transaction decision and do not replace those switch phases.

FILE: under the commit lock validate guards, force immutable after-image blobs, then write/force PREPARED intent and resource reservations. Crash during reservation installation is handled by startup intent indexing before API admission; unaffected resources may remain available. Revalidate guards and reservations, force a single COMMITTED intent marker as logical commit, then install canonical after-images/index pages idempotently and mark FINALIZED. Before COMMITTED, abort clears only reservations belonging to that operation; after COMMITTED always roll forward. Readers use committed after-images until canonical installation finishes. No gameplay/economy effect before commit durability is confirmed. File write/rename/force errors after publication are **unknown outcome**, unlike the current interface's local-failure assumption (`ProfileRepository.java:29–35`); inspect intent ID before reporting failure or compensating. Unsupported atomic rename or directory force must disable co-op transactional activation, rather than inherit the best-effort fallback at `FileProfileRepository.java:761–786`. Power-loss guarantees on the actual filesystem remain owner qualification work.

Redis: PREPARED and reservation install is one bounded script; COMMITTED swaps references, revisions, receipts, indexes and pin sets in one script after checking all guards. Stage large immutable blobs before script entry. Confirm AOF on the same connection for PREPARED and COMMITTED before dependent actions. A lost reply or unconfirmed WAITAOF is not failure-to-commit: hold the gate, query operation status, re-confirm durability and resume. Do not compensate by issuing a fresh inverse transfer. This is stricter than current logged unconfirmed writes (`RedisProfileRepository.java:60–68,805–818,860–879`).

All journals carry separate from/to resource identities, epoch, fence and provider incarnation; membership operations also record affected player Q. Recovered claims are recorded as new recovery authority without overwriting the original evidence. Compare fences only for the same resource/provider incarnation. A lower current fence in the same Redis history is an error; a new local incarnation requires CAS/state reconciliation, not numerical comparison. Preserve old type-5 trailer parsing during import (`ProfileRecords.java:249–284`).

| Intent | Prepared durable evidence | Commit and recovery |
| --- | --- | --- |
| Member switch | Frozen player/session generation, A, exact from/to member heads/epochs, `fromSnapshotId`, P fences if held, Q fence, deadline, intended active account | Preserve current cancellation/phase behavior. Account active pointer + receipt is commit. Before commit restore exact from snapshot; after commit authoritative target restore. Timeout after commit cannot undo it. |
| Membership add/remove/role | M, affected A, old/new member epoch/role, source head, planned account index and name effects, salvage source disposition | Commit metadata/account/head changes together logically. Removed member is gated before source capture; replay installs same removal, never removes a later epoch. Owner removal/ownership transfer refused in this port. |
| Invite accept | Invite ID/revision/expiry, inviter authority at issue, accepting player Q/A, current M/rules/capacity, allocated new epoch | One commit consumes invite, creates membership/head, adds account access. Replay returns same epoch. Expiry checked at commit, not just list time. |
| Kick vote | Vote ID/revision, target epoch, electorate epoch list and approvals, M | Cast records one approval per eligible member. Execution commits vote result with the membership-removal intent; retries do not create another salvage. Target OWNER always refused. |

Exact pins use `(profile,member,epoch,snapshotId)` across **all** pending switch, membership, delivery and transfer intents, not just the profile owner's journals. Add a reverse pin index with reference counts maintained by commit; corrupt/missing pin metadata disables pruning for affected streams. Keep pins through canonical installation and any player recovery; terminal-but-not-restored delivery is still pinned. Current pins are account-journal based (`FileProfileRepository.java:622–645`; `RedisProfileRepository.java:149–164`), so these must expand together.

Membership decisions: roles follow slice-1 permissions (`ProfileRole.java:3–32`). OWNER/MANAGER may invite/start votes; only OWNER changes roles; unique OWNER cannot leave/be kicked or transfer ownership in these slices. Each co-op counts toward the existing account slot cap; maximum 64 memberships and 64 members/profile. Rejoining allocates a fresh epoch and empty initial personal state. Legacy item adoption is first-ever migration only. Names shown in an account slot are per-account aliases stored with that account membership index, unique under normalized lowercase ASCII comparison (1–32 characters `[a-z0-9_-]`). Create and invite acceptance allocate a CuteNames base plus the smallest available numeric suffix, truncating the base to fit, under Q/A reservation; retries reuse the intent’s chosen alias. Alias rename affects only that account. Shared profile displayName is a separate non-unique label changed by OWNER under P/M; it never changes another account’s alias. Store both explicitly and never derive uniqueness from UUID alone.

Vote decision: frozen electorate is all current non-target members including OWNER; require unanimous approval, matching the intent of `KickVote.java:37–38`. Membership or role changes cancel an open vote; require a fresh vote. Default expiry 24 hours, invite expiry 7 days, commit time authoritative. Decline closes the vote. These are proposal policy choices, not existing engine behavior. Unknown external consumer permission semantics must not override repository membership checks.

## 6. Member switching, login, capture and adapters

Preserve switch admission, deadlines, isolation flags, cancellation-aware apply, exact rollback, uncertain commit handling and bounded queue (`ProfileEngine.java:1216–1259,1345–1374,1424–1530,1685–1701`; `PlayerStatePort.java:29–42`). Add a per-player reservation/generation spanning every entity callback. A save capture ticket contains Q token/fence/incarnation, sessionGeneration, A, active profile, membership epoch, M, R and snapshot ID, recorded **before** capture. Post-capture and repository commit compare all relevant fields. An A→B→A return cannot pass because A/session generation changed. Apply this to `saveCaptured`: quit receives a ticket minted before entity capture, not bare state. If no ticket is available, gate and defer; never infer attribution from whichever profile is active later (`ProfileEngine.java:376–398,415–431`; `ProfileRuntime.java:435–473`).

Authoritative login: hold gameplay gate from join, acquire Q, resolve all intents for player and active membership, read the exact committed head, prevalidate required adapters and destination, replace isolated state on entity thread, verify completion and then release gate. Never accept vanilla playerdata as newer merely because login loaded it. If absent head is UNINITIALIZED, initialize empty state under CAS; do not capture existing inventory into every newly joined co-op. Failed/offline apply leaves durable recovery pending. Quit/rejoin waits for prior capture/commit completion or reconciles its intent before a new generation is admitted. Current `prepareActive` is a world return path and not sufficient by itself (`ProfileEngine.java:632–706`).

Required adapters add explicit required/missing/validate hooks while preserving registration-version freezing and unknown-blob carry-forward (`ProfileStateAdapters.java:35–48,86–161`). A required absent, version-mismatched or failing adapter prevents apply/unfreeze; optional unknown data remains unchanged. Budget overflow must refuse a transactional capture rather than silently drop required or preserved unknown bytes. Existing limits remain 32 entries, 2 MiB/entry, 6 MiB aggregate (`ProfileState.java:46–55`), with 8 MiB total state (`ProfileSnapshot.java:17`). Replacing inventory/state must be idempotent; adapters that perform additive side effects cannot participate in authoritative replay without their own operation receipt. Registration changes during a switch invalidate the captured adapter-set generation and require retry/recovery. Do not claim StateCategory values isolate skills/minions/etc without registered enforcement.

## 7. Salvage: consume source, then deliver exactly once

Decision: do not expose the WIP “give items then toggle claimed” operation. Exactly-once here means **one committed movement of isolated item ownership between durable member snapshots**, with idempotent full-state restore before gameplay. It is not an exactly-once arbitrary Bukkit callback. The existing state port provides capture/apply, not a transactional delivery receipt (`PlayerStatePort.java:23–42`). Until slices 3–5 supply the protocol, salvage remains disabled.

1. Removal gates the source player and waits for its final captured snapshot under Q, A/M/R checks. If offline, use its exact committed head. If the source session cannot be fenced/gated, removal stays pending. Extract only isolated inventory/ender-chest items into an immutable payload; no XP, bank, purse or unknown adapter blob is copied. Non-isolated categories cannot be salvaged. Pin exact source snapshot and checksum.
2. Commit removal, account access change, old epoch head `CONSUMED`, salvage `AVAILABLE`, and a durable account cleanup obligation `(removed profile, epoch, removal opId, isolated category mask, cleanup snapshotId)` in one logical transaction. The cleanup snapshot contains the source state with extracted item sections emptied; it does not copy those items to another profile. Account cleanup applies even if removal leaves `activeProfile=null`. On next login, before any gameplay or legacy adoption, resolve cleanup obligations: replace the revoked isolated state with the cleanup snapshot (or the valid newly active profile snapshot), record a Q/A-guarded cleanup receipt, then admit only if a valid active profile has been restored. Crash before receipt repeats replacement while gated; crash after receipt cannot resurrect vanilla items because authoritative login/cleanup receipts prohibit fallback adoption. Keep a permanent `legacyAdoptionClosed` account flag once migration or first authoritative activation occurs. A removed player with no active profile must remain gated on an authoritative empty/cleanup head until choosing a valid profile (or disconnect with a recovery message); do not allow ordinary gameplay or fall through to vanilla login. Source snapshots can remain on disk for recovery, but every restore requires a current admitted epoch and READY head. Rejoin always creates a new epoch with empty item state, never falls back to the retained old stream. This closes salvage/rejoin duplication independently of eventual pruning.
3. Claimant must be a current authorized member **with this profile active**, matching A, Q, sessionGeneration and membership epoch both at capture and commit. Acquire P and claimant operation reservation. Freeze claimant, capture with the §6 ticket, prevalidate capacity and construct a deterministic destination full snapshot containing captured items plus salvage exactly once. Never drop excess items into the world. If inventory cannot hold the complete delivery, return capacity failure and leave salvage AVAILABLE.
4. PREPARE delivery intent with old destination snapshot, new destination snapshot, salvage ID/version, source consumption proof and request digest. COMMIT publishes destination head R+1 and marks salvage `DELIVERED` with that exact destination snapshot/operation ID. The receipt is part of that commit, before entity apply. No independent item grant occurs.
5. Replace the claimant's isolated state with the committed full snapshot through the entity scheduler. On success finalize/unfreeze. On apply failure, disconnect, timeout, crash or lease loss, keep RECOVERY_REQUIRED and restore that same authoritative state at next valid login. Do not refund/reoffer salvage merely because delivery apply failed. On replay, the receipt returns the same result; recovery replaces state rather than adding items. Once finalized, later retries return receipt and **do not** reapply the old snapshot over subsequent gameplay/saves.
6. After a crash before COMMITTED, no delivery was exposed; clear reservations and retry AVAILABLE. After COMMITTED, roll forward even when reply/ack was lost. Record/pin cleanup cannot remove a nonfinalized destination or source. Ordinary capture/switch/save is blocked while the delivery reservation exists, so it cannot overwrite the post-delivery head with a pre-delivery capture.

This closes both reviewed salvage paths (retained source restore; delivery into another active profile) and the mark-before-delivery loss / mark-after-delivery replay dilemma. The save A→B→A path is closed by §6, including quit tickets. A delivered item may later be spent/moved normally; receipts prevent grants, not lawful later consumption.

**OWNER DECISION OD-3 — gameplay durability boundary:** options: (a) enable salvage only where every relevant item interaction/adapter is covered by the freeze and authoritative restore contract, accepting recovery to last durable checkpoint; (b) keep salvage disabled until a broader transaction-aware gameplay layer exists. Recommend (b) until owner crash/replay cases establish (a)'s supported scope. Existing freeze handlers are `ProfileRuntime.java:503–562`, and PM-028 remains open (`docs/releases/BUILD-50-READINESS.md:75`). Uncontrolled plugin inventory changes, cross-player trades, or external side effects during a gate invalidate the premise; this proposal does not claim to prevent every server-wide duplication scenario. A provider exposing only additive delivery without durable idempotency is unsupported, not “best effort exactly once”.

## 8. Shared bank, personal bank and external purse

Decision: store all bank balances under S, separate from member snapshot R and profile metadata M. Personal balances are keyed by membership epoch so rejoin cannot inherit a removed epoch's money accidentally. Membership removal freezes that subaccount; automatic redistribution is out of scope. OWNER/MANAGER may withdraw shared funds; any active member may deposit or operate its own personal subaccount. Internal personal↔shared transfers debit and credit in one guarded transaction with one receipt. Administrative mint/burn is not disguised as a transfer and is not exposed by this port.

Redis scripts must not use `tonumber`, Lua addition/subtraction, or sorted-set scores for monetary values. Compute checked balances in Java from the exact read S, encode complete immutable after-images, and have Lua CAS the exact S and compare reservation/amount strings before installing those bytes; S CAS prevents concurrent lost updates. Canonical decimal strings preserve Long values in index/receipt metadata. Amounts are positive signed-long minor units, fixed provider/currency/scale identity; use exact decimal-to-minor conversion, checked add/subtract, reject negative/zero, insufficient available balance, capacity overflow, and Long overflow before writing. Capacity 0 means no policy cap but still Long.MAX_VALUE. Reserve amounts when an external transfer is pending; available = posted minus reserved. Currency/scale/backend changes require a separate offline migration, never an implicit reinterpretation. Collections/contributions use checked nonnegative arithmetic and bounded keys; they are not proof of external economy enforcement. Current repository guards supply the commit foundation (`ProfileRepository.java:16–20`; `RedisProfileRepository.java:121–130`); the WIP bank counters alone did not supply a purse transaction (historical review input, `W:ProfileEngine.java:1199,1260`).

Purse boundary: the historical `ProfilePurse` interface is external-provider plumbing, not an implementation (`W:sourbyapi/src/main/java/dev/iyanz/sourbycraft/api/profile/ProfilePurse.java:7`). SSB provider format, availability and guarantees are **unknown** in this baseline. Do not implement a transfer using independent `balance/setBalance` calls or assume Vault/SSB calls are transactional.

Proposed capability `TransactionalProfilePurse` must offer `prepare(opId,player,profile,epoch,currency,delta,expectedVersion)`, `status(opId)`, `commit(opId)` and `abort(opId)` with durable idempotency and request-digest conflict detection; preparation reserves funds/capacity, commit is eventually retryable after preparation, status survives restart. External calls run on the provider's declared scheduler, never block an entity thread or the shared I/O lane. Gate profile switching while unresolved, and forbid another purse snapshot adapter from independently overwriting the same balance.

Transfer protocol: write durable intent and bank reservation; prepare external purse; record its durable prepared token; atomically commit the internal bank posting plus immutable COMMIT decision/receipt; then retry external commit to completion. Before internal COMMIT decision, abort external preparation and release bank reservation only after confirmed abort. After decision, never abort/refund on timeout: reconcile by opId until external commit is confirmed, then finalize. Keep credited bank funds unavailable until external completion. If a prepared provider operation can expire or become uncommittable without a durable status, it fails this capability and transfer stays disabled. Receipt lookup settles lost replies; operator tooling reports pending/unknown, not successful transfer.

**OWNER DECISION OD-4 — provider:** (a) require the transactional capability above; (b) ship bank-only operations and defer purse transfers. Recommend (b) until the external provider is inspected and separately approved. There is no safe generic exactly-once bridge to an uncooperative purse API. The same replay receipts apply to bank-only transfers.

## 9. Bounded reads, indexes, receipts and overload

The current codec bounds payload allocation and FILE reads the actual stream with a sentinel byte (`ProfileRecords.java:40,64–84`; `FileProfileRepository.java:769–778`). Preserve this for every new reader; never substitute `Files.size` + `readAllBytes`. Current Redis journal caps are 64/player and 1024 status entries (`RedisProfileRepository.java:79–85`); new listings need their own bounded indexes, not scans of all records.

Proposed hard limits (configuration may lower, not raise them in schema 1):

| Surface | Limit / behavior |
| --- | --- |
| Member/account lists | 64 each; no unbounded historical epochs inside metadata |
| Metadata | Existing 32 entries/key 64 chars/value 512 chars; encoded UTF-8 also capped by record budget |
| Control records | 64 KiB each; shared record 256 KiB; intent 256 KiB of refs, no embedded snapshots |
| Snapshot/salvage item blob | 8 MiB payload + 64 KiB framing allowance; item lists respect `ProfileState.MAX_ITEMS=256`; one blob per payload, no arbitrary aggregate read; extraction serializes inventory and ender-chest sections separately with original slot tags |
| Invite admission | 64 open/profile and 64 open/invitee; expired records do not consume slots after bounded cleanup transaction |
| Votes | 1 open/profile; at most 63 eligible voters; archive separately |
| Salvage | 64 outstanding/profile, up to 512 MiB referenced bytes; if full, refuse removal before consuming source; never evict undelivered items |
| Pending operations | 64/account, 64/profile, global 1024 admitted locally; recovery work bypasses new-operation admission but uses bounded pages, not unbounded memory |
| Listing page | 32 records, 256 KiB decoded control bytes, opaque cursor; salvage lists return summaries, never item blobs |
| Cleanup / recovery batch | 32 records or 256 KiB metadata per I/O step; yield through existing queue before next batch |
| Receipt retention | No expiry-based loss of replay protection; compact terminal receipts to paged permanent `(opId,digest,outcome)` entries; 1,000,000 receipts/resource then refuse new financial/delivery operations pending offline archival policy |

API operation IDs are server-issued UUIDs bound to actor and request digest. Permanent receipt lookup is point-indexed; retry after archival cannot become a fresh operation. Do not use TTL to delete spent salvage or transfer identity. A bounded permanent count is deliberate fail-closed admission; archival beyond that cap is a future schema/owner policy, not silent deletion.

FILE maintains durable paged indexes by invitee and profile for invites; by profile/target for votes; by profile/state for salvage; by player/profile for intents and pins. Sorted order is `(createdAtMillis, UUID)`, with cursor containing index generation, last key and scope; changing index generation invalidates cursor with restart-required listing response, not an incomplete authoritative answer. Index pages are type 13, at most 128 entries/64 KiB. Index writes participate in intent after-images. On startup stream index pages/replay pending intents; no request-time directory scan. Missing/corrupt index locks affected operations until an offline, bounded-memory rebuild checks canonical records. Never return “empty” after a corrupt authoritative read.

Redis uses matching sorted-set indexes plus count/byte counters changed in the same scripts as records; page with bounded ZRANGE/LIMIT and point-fetch at most 32 bounded records. Avoid HGETALL, KEYS, full SMEMBERS or unbounded Lua loops for new listings/pins. Snapshot blobs are separate GETs only when explicitly needed. Before retrieving a Redis blob check its stored length via a bounded-read mechanism/script and enforce actual client response limits; a metadata length check alone is not protection against a concurrent oversized reply. Large blobs are immutable once staged and hash-verified at publication. A response cap is an implementation requirement to add in `sourbycraft-server/src/main/java/dev/iyanz/sourbycraft/awf/redis/RedisClient.java`, not a claim about the current Redis client. Add a bounded bulk-response call for profile reads that checks RESP bulk length before allocating, closes/discards the connection on over-limit response, and never returns a truncated frame. Use it for every co-op blob read; do not change generic callers silently.

Admission and expiry happen under P/CAS with repository time (Redis TIME; FILE injected clock with nondecreasing effective time). Clock rollback does not revive expired invitations. Receipt and pending-pin retention never depends on wall-clock expiry. FIFO saturation returns a retryable capacity error before side effects; never run repository work inline on the entity thread or add an executor per member (`ProfileIoQueue.java:23–25,49–57`). No throughput claim follows from this design.
