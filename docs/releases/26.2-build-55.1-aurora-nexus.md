## What is in Build 55.1

Both keys are RESTART_REQUIRED and **off by default**; with the defaults the server behaves as Build 55. No record
type or store level changes.

### 1. Session handoff wait on a proxy server switch (B1)

See [DISTRIBUTED-OWNERSHIP.md](../awf/multiprofile/DISTRIBUTED-OWNERSHIP.md#session-handoff-on-a-proxy-server-switch-build-551).

- Behind Velocity a `/server` switch logs the player in to the new server before the old one sees their quit. The new
  server's join attempted the strict session claim `Q` once, almost always before the old server had committed the
  quit save and released the claim, so nearly every switch was kicked with "Your profile is active on <node>. Try
  again in a moment." Nothing was duplicated or lost (the login gate kept the new server's vanilla playerdata out of
  every save); the experience was the problem.
- New key `aurora.awf.multiprofile.coordination.handoff-wait-ms` (default `0` = the Build 55 single attempt;
  `5000` recommended behind a proxy; ceiling `15000`). A join refused only because another live session holds `Q`,
  or another node holds the active profile's node claim, retries the claim with bounded backoff (100 ms doubling to
  1 s, never past the window) until it is granted, the player left, the engine closed or the window elapsed, in which
  case the Build 55 refusal is returned unchanged.
- **Fencing is not weakened.** Every retry is the same strict claim; it succeeds only once the holder released the
  claim or its lease lapsed under the existing epoch rules. The old server releases `Q` after its quit save settled
  (committed, or failed and logged with the marker left open), so the admitted join restores the last committed head
  exactly as any Build 55 authoritative login does. The wait never takes a live claim and never touches the
  holder's fence or epoch; a crashed old server still refuses the join until its TTL, which is why the ceiling is
  well below it.
- The retries are queued by one daemon timer thread (`SourbyCraft-AWF-profile-handoff`) and run on the profile I/O
  lane; no region or global tick thread waits. Shutdown ends a wait with the refusal, so the join's gate is released;
  a join on an already closed engine fails before any attempt, as in Build 55.
- **Frozen while waiting:** the player stands on the join's vanilla playerdata behind the Build 53 login gate (item,
  experience and interaction events cancelled, nothing captured) with one action bar, "Loading your profile...".
  New `HandoffFreeze` listener: all damage to and by the player (no death, no drops), every command, inventory
  opening, movement to another block and portal use are cancelled for a waiting player, on the owning region thread.
- `/perf multiprofile` gains the rows "Session handoff": claim waits started / admitted / timed out / left / failed
  (one join can wait twice: `Q`, then the node claim), and the p50/p95 of the admitted waits.

### 2. Preserving a REQUIRED adapter's data on a node without its plugin (B3)

See [CONFIGURATION.md](../awf/multiprofile/CONFIGURATION.md) (`adapters.preserve-unregistered`).

- SSB-AuroraProfiles registers its purse adapter `economy` as REQUIRED whatever `economy.backend` says, including
  `native` (owner choice: Atrium-native shared money): every capture stores `P1|native|<decimal>` per profile and the
  snapshot's required record names `economy`. A node without SSB2 (the lobby) registers no such adapter, so every
  lobby login restore of a player with a saved purse was refused `ADAPTER_MISSING`.
- New key `aurora.awf.multiprofile.adapters.preserve-unregistered` (default `[]`): adapter ids whose stored REQUIRED
  data passes through the node **unchanged while no plugin registers them there**: not applied, not captured,
  carried forward by every merge together with the stored required record, no `ADAPTER_MISSING`. The island applies
  the purse again from the carried bytes. A registered id is never affected: an UNSUPPORTED or older registration
  still refuses. An id an apply passed through for a player is remembered until that player's next apply of it or
  their quit, so a plugin registering the id mid-session is not captured for them (the stored bytes are carried
  forward) and never overwrites data this node did not apply. The lobby sets `preserve-unregistered: [economy]`;
  the island sets nothing. WuretaBridge therefore does not need to register a copy of the adapter.

### Not changed

- Co-op across nodes (split-plan B2, OD-1): a co-op profile is on one node at a time; a node claim its other members
  keep is waited out and then refused as before. `coop.enabled: false` on a Lobby + Island pair stays the only
  correct configuration.
- No proxy handoff transport, no routing of players, no live-state transfer: the admitted join restores the last
  committed snapshot.

## Owner test cases

The test sources were written by agents and **never run by them**. CI runs them on push:
- `SessionHandoffTest` (wait admitted after the release under a higher fence; window elapses with the refusal while
  the holder's claim stays live; default 0 is one attempt; a stale join and `close()` end a wait; the node claim waits
  under the same window; a closed engine fails before any attempt; metrics rows). `HandoffFreeze` has no unit test.
- `AdapterPreservationTest` (listed unregistered REQUIRED data passes `validateApply`/`apply` and is carried
  byte-identical with the required record; unlisted or registered ids keep the Build 53 refusals; a mid-session
  registration is not captured over passed-through data until the next apply)
- `ProfileSettingsBuild551Test` (both keys: defaults, old constructors, parsing, fallback, ranges, AuroraKeys rows)

Manual cases (two SourbyCraft nodes behind Velocity, `mode: distributed`, Redis repository, `coop.enabled: false`,
`handoff-wait-ms: 5000` on both, `preserve-unregistered: [economy]` on the lobby only):
- **TO-B55.1-01:** switch island → lobby → island repeatedly, alone and with several players at once: no kick, the
  action bar shows while waiting, the player arrives with the state they left with (inventory, purse on the island),
  `/perf multiprofile` counts admitted waits and no timeouts.
- **TO-B55.1-02:** kill the island mid-switch (`kill -9`): the lobby join is refused with "Your profile is active on
  <island>" until the fabric TTL lapses, then admitted with the last committed snapshot; nothing duplicated.
- **TO-B55.1-03:** restart Redis during a switch: the attempt fails and the join is refused with the error named;
  a reconnect after Redis is back is admitted.
- **TO-B55.1-04:** with `preserve-unregistered: []` on the lobby, a player with a saved purse is refused
  `ADAPTER_MISSING` at the lobby (Build 55 behaviour); with `[economy]` they join, play the lobby, return to the
  island and keep the exact purse; `/awf multiprofile status` and the audit log show no adapter failure.

## Known limits

- The handoff wait covers the joining side only; a proxy that keeps the old connection open after the new one
  joined (Velocity does not) would wait out the window and refuse.
- A `timed out` count that rises means the previous server's quit save takes longer than the window (Redis
  `WAITAOF`, storage latency) or that server is down; raise the window within the ceiling or fix the storage.
- `preserve-unregistered` trusts the operator: an id listed on a node where its plugin was merely forgotten is not
  applied there (its data is still never dropped). It never relaxes a registered adapter.
