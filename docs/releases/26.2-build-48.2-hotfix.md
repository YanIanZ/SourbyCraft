Build 48.2 fixes three faults found on the Sourby Demo panel (Epic Skyblock v9.7 setup on v26.2-r48.1,
2026-10-22). Each is a port of a fix merged on `26.2`; the Build 49 work merged there is not included.

## What changed

### A Paper-made world keeps its saved overrides (26.2 #41)

`paper:level_overrides` written by Paper has neither `Aurora.Distance` nor the old `Canvas.Distance` key.
`PerWorldDistanceConfig.LEVEL_OVERRIDES_FIELD` returned an error there (`Failed to parse saved data for
'SavedDataType[paper:level_overrides]': No key Aurora.Distance`), so the whole record was dropped and rebuilt
from the root world: such a world lost its own spawn, game time, game type and difficulty, and the next save
wrote the replacement. Now a missing key means "no distance override"; the new key still wins over the old
one, the deprecation line is logged only when `Canvas.Distance` is read, and a malformed value is still an
error. The readers return a fresh unset config instead of the shared `DEFAULT` (whose references are mutable).
Tests: `PerWorldDistanceLegacyKeyTest`.

### `MinecraftServer.currentTick` for FastAsyncWorldEdit (26.2 #42)

FastAsyncWorldEdit's `v26_2` adapter (2.15.4 and the latest 2.16.1) reads Paper's
`MinecraftServer.currentTick` with `getstatic`; the region-threading base had removed the field, so creating a
`BukkitWorld` threw `NoSuchFieldError`: WorldGuard failed to enable and Jobs was disabled. Minecraft feature
patch **0077** (0083 on `26.2`) declares `public static volatile int currentTick` again and advances it once per
global tick (`bridge/LegacyServerTick`). It is a global-tick counter, not a region tick, and no server code
reads it. Details: [`fawe-currenttick-compat.md`](../development/fawe-currenttick-compat.md). Tests:
`LegacyServerTickTest`. Also from that change: `scripts/agent_testserver.py --large-plugin-jar` (plugin jars
up to 32 MiB on the agent test server, used to verify this fix).

### World settings during startup (26.2 #44)

Plugins that apply per-world settings while they enable (Multiverse-Core 5.8.1: `setPVP` -> `setGameRule`,
`setTicksPerSpawns`, ...) were refused with `Cannot modify server settings off of the global region`, and
Multiverse logged `Failed to load configuration` for every world. Paper feature patch **0025** routes the 12
`CraftWorld` world-settings setters through `guards/WorldSettingsOwner`: before the region scheduler starts the
server's startup thread may change them (as on Paper); once regions tick only the global tick may (unchanged);
the shutdown thread always may. Region ownership checks are unchanged; inherited-guard ledger `F-GLOBAL-TICK`
29 -> 17 sites. Details: [`multiverse-world-settings-compat.md`](../development/multiverse-world-settings-compat.md).
Tests: `WorldSettingsOwnerTest`, `RegionOwnershipContractTest`. Known limit, unchanged: Multiverse's import of a
world without a stored spawn still reads blocks before any region owns them and is refused.

## Identity and the auto-updater

`/ver` and the startup banner say `Build 48.2 — Aurora Nexus`; `sourbycraft-build.properties` has
`buildNumber=48.2`; the manifest `Build-Number` stays `48` (Paper parses it as an integer). The auto-updater
orders `48 < 48.1 < 48.2 < 49`: Build 48 and 48.1 servers are offered 48.2 (installed only where
`apply-mode = "auto"`), and the next 26.2 release (Build 49) supersedes it.

## Not in this hotfix

Everything else merged to `26.2` after `v26.2-r48` (Build 49 configuration layout and console design, Build 50
hook refactors, updater rollback fixture, level.dat writer, and the rest). Those ship with Build 49/50.
