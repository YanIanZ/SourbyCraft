## What is in Build 54

MultiProfile and co-op stay **off by default**. With MultiProfile disabled, the server behaves as Build 53. With co-op
disabled, the bank and salvage calls answer `COOP_DISABLED`.

### 1. Profile types managed by plugins (owner decision 2026-11-04)

Profile types, their naming and their rules can be defined by a consumer plugin, such as the SSB-AuroraProfiles
SuperiorSkyblock addon from its own `types.yml`. See [PROFILE-TYPES.md](../awf/multiprofile/PROFILE-TYPES.md).

- **API:**
  - `ProfileTypeRegistry` is a Bukkit service, also reachable through `AuroraProfiles.typeRegistry()` and
    `SourbyAPI.profileTypes()`.
  - Supporting types: `ProfileTypeDefinition` (id, display name, co-op allowed, creatable, max members, naming, rules),
    `ProfileRule` (allow/deny with parameters), `ProfileNaming` (server pool or the type's own pool), `ProfileRuleSet`
    and `ProfileTypeSource`.
  - Queries: `rules(profileId)` and `allows(profileId, action)`.
- **Engine-owned actions** are gated with `ACTION_FORBIDDEN_BY_TYPE`: `bank.deposit`, `bank.withdraw`,
  `bank.personal`, `bank.transfer`, `coop.convert`, `coop.invite`, `coop.accept`, `salvage.claim` and
  `collections.contribute`.
  - A transfer also needs `bank.personal`, plus `bank.withdraw` or `bank.deposit` depending on direction. So a type
    that denies deposit and withdraw ("Ironman: no bank") has no route left to move money in or out.
  - Actions owned by the consumer, such as the SSB2 island bank, are checked by the consumer through `allows`.
- **Built-in types:**
  - The built-ins are classic, ironman, stranded and bingo. A consumer can override them
    (`types.registry.allow-override-builtins`).
  - The built-in ironman and stranded deny only `trade`, `auction` and `bazaar`. The "no bank" rule comes from the
    consumer's definition.
- **A deny is never lifted silently.**
  - Definitions are persisted: FILE under `types/`, Redis in `mp:types`. A consumer that unregisters or disables
    leaves its last definition in force.
  - An unreadable definition becomes a deny-all tombstone, including for a built-in override.
  - A type with no definition is denied (`types.unknown-type-policy: deny`).
  - The first profile of a registered type, or a built-in override that denies an action, raises the store to
    **Build 54**. The updater then refuses to downgrade.

### 2. Shared bank, personal bank, collections (COOP-DESIGN slice 6, G3)

- **Banks:**
  - The shared bank and personal bank follow `aurora.awf.multiprofile.bank.*`: currency, shared capacity,
    `personal-cap-percent` 20 and `interest-percent` 10, all RESTART_REQUIRED.
  - Interest can be applied at most once per `interest-interval-hours`, default 24, measured on the store clock.
- **Collections** have a per-member contribution ledger.
- **Transfers** between the shared and personal bank are intents with permanent receipts. They refuse to overflow,
  work in integer minor units, and work on both FILE and Redis.
- **Idempotent retry:** ledger calls accept a caller operation id. A retry with the same id and the same request is
  REPLAYED before any validation, and the operation id is available in `ProfileOperationException.operationId()` and
  through `bankReceipt`.
- **Removed members:** their personal balances and contributions are archived, so the bounded records keep working on
  long-lived co-ops.
- **Purse (OD-4):** the purse stays per profile through a REQUIRED adapter, and purse↔bank transfers are refused
  with `PURSE_TRANSFER_UNSUPPORTED`.

### 3. Salvage exactly once (OD-3)

- The items of a removed member are delivered to a claimant who has that profile active.
- The source is consumed before delivery, and a durable receipt is written.
- A full inventory loses nothing: the rest stays claimable.
- After a crash, nothing is duplicated: before the commit point the claim aborts, after it the claim rolls forward.
- A delivery hold blocks every save path until the apply succeeds, and the capture is bounded by
  `switching.timeout-ms`.
- The first delivery raises the store to **Build 54**.

### 4. Developer API (owner decision 2026-11-04)

- `SourbyAPI`, one static entrypoint: `worlds()`, `profiles()`, `profileTypes()`, `metrics()` and `build()`. A feature
  that is off throws `FeatureUnavailableException`, which names the config key that enables it.
- `AuroraWorlds` additions:
  - `listWorlds()`, `info(name)` (`AwfWorldInfo`), `listTemplates()` and `isAwfWorld(World)`.
  - `createInstance(template, name)` creates a disposable instance. It is never saved, it is deleted once its unload
    is confirmed, and leftovers are removed by a sweep after startup. AWF refuses to attach a world that is being
    deleted.
- New profile API: bank, collections, transfers and salvage, plus the async events `ProfileBankTransactionEvent` and
  `ProfileSalvageDeliveredEvent`.
- Getting started: [sourbyapi/README.md](../../sourbyapi/README.md). The release asset for the `sourbyapi` jar comes in
  Build 55.

## Known limits

- Redis type definitions are read at startup only. Other nodes see a new registration after their restart.
- FILE permanent receipts are listed on first use for each resource, and the cap is 1,000,000 per resource.
- Staged blobs left by a refused prepare are not swept. Applying salvage replaces the isolated state captured at the
  claim.
- A transfer or claim reserves the profile record, so concurrent membership operations on a busy co-op may get
  `STALE_STATE`.
- Profiles whose free-form metadata already holds `aurora:type` now resolve to that type.
- Coming in Build 55: audit, switch guard, rule coverage, per-account I/O queue (PM-091), developer guide and example
  plugin, the `sourbyapi` release asset, and the addon port.
