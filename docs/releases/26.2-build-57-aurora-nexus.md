## What is in Build 57

No new configuration key. Both changes are LIVE with no setting; the first one depends on the existing
`aurora.bridge.mode` / `aurora.bridge.thread-checks` values as the table below says.

### 1. Off-region player reads get a world-wide snapshot instead of an exception

See [aurora-plugin-bridge.md, "Off-region world reads"](../architecture/aurora-plugin-bridge.md#off-region-world-reads-build-57).

- **The problem (WuretaMC Hub, Build 56, `aurora.bridge.mode: safe`, `thread-checks: relaxed`).** One log held 646×
  `[SourbyCraft] Bridged plugin Shopkeepers generated an exception while executing task 8` with
  `java.lang.NullPointerException: Cannot invoke "RegionizedWorldData.getLocalPlayers()" because the return value of
  "Level.getCurrentWorldData()" is null`, plus Shopkeepers' own follow-ups ("Error during ticking!", "Cannot remove
  entities while the AI task is running!": its AI task died mid-run and never cleared its running flag).
- **Where it really came from.** Not `CraftWorld#getPlayers` (that reads the world-wide `ServerLevel.players()` and
  cannot NPE). Shopkeepers 2.28.1's `EntityAI` task ticks each shop mob's `Sensing` and `GoalSelector` through NMS
  (`compat.v26_2_R1.CompatProviderImpl.tickAI`, read with `javap` from the Hub's jar; no execution), and
  `LookAtPlayerGoal` → `ServerEntityGetter.getNearestPlayer` → `Level.getLocalPlayers()` dereferences the region data
  of the current thread. Task 8 is untargeted, so the bridge runs it on the global tick thread, which owns no region:
  `getCurrentWorldData()` is `null`. The same path is reached by `World#spawnParticle` (`sendParticles`),
  `getRandomLocalPlayer`, `hasNearbyAlivePlayer` and every AI sensor from a thread that ticks no region of the world.
- **The fix** (MC feature patch 0088 "world-wide player snapshot for off-region readers",
  `guards/OffRegionWorldReads`, hook-first: one call in `Level.getLocalPlayers()` and one in
  `ServerLevel.getLocalPlayers(selector, max)`; the on-region check is in the patch, the guard names no engine type):
  on the thread that ticks a region of the world nothing changes. Off every region of that world, a **bridged
  plugin's task body while `thread-checks` is `relaxed` or `bridged`** (the marker also covers code the body calls on
  that thread) or **any caller while `thread-checks = relaxed`** gets an immutable world-wide copy of
  `ServerLevel.players()` (a `CopyOnWriteArrayList`; one array copy, no region lock, taking it never blocks). Every
  other caller (`enforced`, bridged bodies included; Folia-native plugins and the server under `bridged`) keeps the
  base's exception, so strict semantics are not widened. Each snapshot is counted (`/perf plugins`, "Off-region player
  snapshots") and announced by one WARN per (plugin or thread, world) per 60 s naming the plugin, task and world.
  **Honestly:** the caller is still on the wrong thread, and some callers of `getLocalPlayers` mutate (the entity
  tracker's add/clear, raids, beacons, the dragon fight touch player-side state); off their region they used to fail
  fast and while relaxed now proceed -- one more accepted LightingLuminol race. Shopkeepers' `getNearestPlayer` path
  only does distance arithmetic over the copy.
- **Audit of the Bukkit `World` accessors.** `getPlayers()`/`getPlayerCount()` read the world-wide list already;
  `getEntities()`, `getLivingEntities()`, `getEntitiesByClass(es)` and `getEntity(UUID)` go through Moonrise's
  `EntityLookup.getAll()`, which copies the world-wide list under its own lock; none dereferences
  `getCurrentWorldData()`, so no entity snapshot was added. The remaining `ServerLevel` reads of it are routed by MC
  0082/0085 or, as far as the grep of `paper-server` callers went, not reached from the Bukkit API.

### 2. Bridged exception log: one stack trace per signature, one summary per minute

See [aurora-plugin-bridge.md, "Bridged exception log"](../architecture/aurora-plugin-bridge.md#bridged-exception-log-build-57).

- `Bridged plugin X generated an exception while executing task N` is deduplicated by signature: plugin, class of
  the plugin's task body (Paper feature patch 0030 names the `Runnable`/`Consumer` class), exception class and top
  stack frame (`bridge/ExceptionSignatures`). First occurrence: full stack trace. Repeats inside 60 s: counted, not
  logged. First repeat after the window: one line, no trace, `repeated N time(s) in the last 60 s (M in total)`.
  Bounded: 256 signatures per bridge runtime, least recently seen evicted.
- `/plugins <name>` shows "Task exceptions (total / signatures)" and the three most frequent signatures;
  `/perf plugins` one line per plugin. Quarantine, `ViolationClassifier`, `GuardViolations` and the relaxed-hit
  accounting are unchanged; an ordinary exception still never quarantines.

### Not changed

- No change to `aurora.bridge.*` defaults, routing, admission or quarantine thresholds.
- No entity snapshot: the audit found none needed (above). Should a plugin hit another `getCurrentWorldData()`
  dereference off a region, it is a new site, not covered here.
- Shopkeepers itself is not made region-aware: its AI task still runs on the global tick thread and reads shop mobs
  owned by regions it does not tick, which the relaxed checks allow and count.

## Known limits

- The snapshot is the world's player list at the moment of the call; a region-local list would be a subset. Callers
  that compute "nearest player" get the nearest of all players in the world, which is what a single-threaded server
  answers.
- The WARN is per (plugin, world); a plugin reading two worlds logs two lines a minute.
- Exception signatures keep the top frame only; two bugs in one method at different lines are two signatures, the
  same bug reached from two task classes is two signatures. An evicted signature (past 256) is logged in full again.
