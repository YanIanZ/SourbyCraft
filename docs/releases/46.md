# SourbyCraft 26.2 — Build 46c, Aurora

Build 46 turns Aurora from a name into an architecture with a boundary, and corrects several
measurements — including two of this project's own published results — that turned out to be
artifacts of how they were taken.

## Aurora engine

- Aurora owns its execution contracts. `OwnerHandoff` states what SourbyCraft needs from whatever
  schedules it — deferral, distinguishable admission, the current owner's identity, and mutually
  exclusive delivery or retirement — without naming a backend. The Folia-derived scheduler is now
  reached from exactly two adapter files, pinned by tests against the file set rather than the
  symbol set, so replacing it is an edit to a known list instead of a search.
- The Aurora region system (`execution/region`) states region identity, topology and lifetime in
  SourbyCraft's own terms. Regions carry a generation as well as an id, because regions split and
  merge as players move and a region id can outlive the region that bore it.
- Engine code SourbyCraft wrote now lives in `dev.iyanz.aurora.*` inside the Minecraft tree rather
  than hiding in a vanilla package. Edits to upstream files stay where the code they change lives;
  whole new classes do not.
- Execution lanes attribute per-thread CPU to the subsystem that spent it, surfaced by
  `/perf lanes` and emitted to JFR. It reports concentration and saturation separately, because a
  server can have one lane doing nearly everything while the machine sits idle — which is exactly
  when adding threads to the busy lane looks obvious and measures worse.
- Startup reports the engine coming up stage by stage. The percentage is stages finished over
  stages declared, never elapsed time; a failed stage is named, and the closing line reads
  *degraded* rather than *online*.
- `aurora.diagnostics.lane-sampling` (LIVE) turns lane attribution off for hosts that do not want
  to pay for it. On an idle server the telemetry lane costs more than the region lane.

## Correctness

- An async path solve is no longer applied to an entity that a dimension transfer replaced, nor to
  a navigation that moved on. Tracing every writer of `PathNavigation.path` found three
  invalidation events, one of them live: the synchronous recompute still runs while a solve is in
  flight, so a result could overwrite a path computed *after* it.
- Solves whose node evaluator writes to the mob are refused rather than raced.
  `AmphibiousNodeEvaluator` saves and restores pathfinding malus around a solve, which could
  restore a value it never saved and corrupt an axolotl's or drowned's walkable cost permanently.
  `Sniffer` writes malus from both pathfinding callbacks.
- `SnapshotPathRegion` no longer dereferences the live level from a worker: the world border is
  captured as a detached copy. Its claim to be "fully immutable" was overstated and is now stated
  accurately, including the live-mob reads it deliberately keeps.
- Replies to a command block run on the region that owns the block. Messaging one writes
  block-entity state behind `AsyncCatcher` and Folia's thread check, so the old direct path threw
  and the failure was swallowed — a command block running `/ping` or `/speedtest` silently got no
  output. Non-player *entity* senders, which `/execute as` produces, were affected the same way.
- Telemetry leaves `WARMING`. Readiness was derived from the longest-lived region generation, and
  regions split and merge as players move, so no generation ever spanned fifteen minutes and the
  state never cleared. A two-hour certified soak reported `WARMING` for all 6302 of its samples.
- Async pathfinding shutdown refuses admission instead of degrading to an inline solve on a region
  thread that is trying to stop, and the four cancellation operations are separate.

## Measurement

The first certified multi-hour soak found no memory leak: across two hours at ten players,
resident memory fell 5.9%, heap after GC fell 1.3%, and tick moved −0.6%.

Two published results from this project were wrong, and both are corrected here rather than
quietly dropped:

- **Every baseline measured world generation.** `run_baseline.py` has always had `--world` and the
  workload notes have always said to use it; no run ever did. Seeded against a pre-generated world
  the same workload runs 41% faster at the mean and 59% faster at p99, uses half the CPU, and
  delivers the ten regions it declares instead of six.
- **The chunk-worker A/B reversed.** Its original finding — that more workers buy tail latency —
  was measured on a workload whose entities silently never spawned, because `forceload` returns
  before the chunks exist and the refusal went to chat where nothing checked it. With entities
  present, six workers are worse at every percentile; seeded, the penalty is a fifth of what was
  reported. The recommendation is unchanged and its justification is weaker.

The harness now survives the runs most worth keeping: a metric the server could not compute
arrives as null through JFR's JSON, and summing it destroyed the entire measurement.

## Validation and limits

Java 25 is required. This release retains the operator's configuration and does not automatically
tune heap, GC, or gameplay settings. Release identity advances from 45 to 46.

Scheduler replacement is not on the near path, and the measurements are why: the region lane is
about a third of consumed CPU at ten players while the machine sits mostly idle, and chunk work —
which dominates — is the same noise mathematics in any architecture.

Async pathfinding remains default-off. The contract work does not qualify enabling it; that needs
a workload measurement nobody has taken. Dense single-point entity spawns remain single-threaded
by construction, because region threading parallelises across space.
