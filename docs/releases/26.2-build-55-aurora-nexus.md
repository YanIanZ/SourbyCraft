## What is in Build 55

MultiProfile and co-op stay **off by default**. With MultiProfile disabled, the server behaves as Build 54. Every new
MultiProfile key is RESTART_REQUIRED, and no new record type enters the profile store format.

### 1. Operations (COOP-DESIGN slice 7, G5–G7)

See [OPERATIONS.md](../awf/multiprofile/OPERATIONS.md#build-55-audit-archive-cooldown-guards-metrics).

- **Audit log** (`audit.enabled`, default on; `audit.retention-days`, default 30):
  - An immutable entry is recorded **after the durable outcome** of every switch (committed, refused, vetoed,
    failed), profile create/delete/lock/unlock/archive/unarchive, every co-op membership operation (and its refusal),
    every bank posting and every salvage delivery.
  - Newest 4096 entries in memory (`/awf multiprofile audit <profile> [cursor]`, `AuroraProfiles.audit`), plus
    append-only daily files `<directory>/audit/<yyyy-MM-dd>.log`, capped at 256 MiB per day. Both are node-local.
  - Audit failure never changes an outcome: a full queue or a capped file drops the entry and counts it; a failed
    write is counted and logged at most once a minute. The audit log is not a recovery journal.
- **Archived (read-only) profiles:** `/awf multiprofile archive|unarchive <profile>` (admin) and
  `AuroraProfiles.archiveProfile`. Mutations answer `PROFILE_ARCHIVED`; reads keep working; a member may still leave
  an archived co-op. Archiving is refused while any member has the co-op active (`PROFILE_LOCKED`) or plays it on
  this node (`MEMBER_ONLINE`). `unarchive` restores a prior operator lock. Stored as `LOCKED` plus a metadata marker,
  so no store level is raised. Seasonal types (built-in `bingo`) are archived by the consumer or an operator, never
  by the server on its own.
- **Switch cooldown** (`switching.cooldown-seconds`, default `0` = Build 54 behaviour): only a committed switch starts
  it; a refusal answers `SWITCH_COOLDOWN` naming the wait. `/awf multiprofile cooldown <player> [reset]`.
- **Switch guards:** plugins register a `ProfileSwitchGuard` (for example a combat or dungeon check). Guards run on
  their own two-thread lane with a 64-deep queue; a hung guard is interrupted at the budget, and a throwing, timed-out
  or queued-out guard is a veto (`SWITCH_VETOED`). The move-out switch made for a member by a leave or kick
  (evacuation) skips cooldown, guards and the target's `profile.switch` rule.
- **Type rules at every engine action boundary:** new engine-owned rules `profile.switch`, `coop.kick` and
  `coop.label`. `profile.switch` does not gate a profile whose type has no definition on the server, so Build 54
  profiles with free-form `aurora:type` stay playable.
- **Per-account I/O ordering (PM-091):** `io.partitions` (default `1` = Build 54 FIFO over all accounts, max 64).
  Above 1, steps of different accounts/profiles run at once while each key keeps FIFO order; steps that touch
  several keys are barriers; in-flight steps are capped at the storage lane's threads.
- **`/perf multiprofile`:** switch latency p50/p95/p99, failed/refused/vetoed switches and guard timeouts, I/O queue
  depth and wait p50/p95/p99, outstanding salvage and kick-vote ages, audit and event drop counters. In-memory,
  reset at restart.

### 2. Developer API completion (owner decision 2026-11-04)

Guide: [developing-with-sourbyapi.md](../guides/developing-with-sourbyapi.md). Example plugin:
[`examples/sourbyapi-example/`](../../examples/sourbyapi-example/) (built by CI with `-PincludeTestPlugin=true`).

- **Aurora scheduler facade:** `SourbyAPI.scheduler()` → `AuroraScheduler`: run on the region of a `Location`, on an
  `Entity`'s scheduler (with an optional `retired` callback), globally or async; now, delayed or repeating; each call
  returns a cancellable `TaskHandle`. `isOwnedByCurrentRegion(Location|Entity)`.
- **AWF events** (`dev.iyanz.sourbycraft.api.world.event`, async, fired after the durable outcome):
  `AwfWorldCreatedEvent`, `AwfWorldLoadedEvent`, `AwfWorldUnloadedEvent`, `AwfWorldDeletedEvent`,
  `AwfWorldSavedEvent`, `AwfInstanceDisposedEvent`.
- **Profile events** (`dev.iyanz.sourbycraft.api.profile.event`, async, informational): `ProfilePreSwitchEvent`,
  `ProfileSwitchedEvent`, `ProfileCreatedEvent`, `ProfileDeletedEvent`.
- **API parity:** `ProfileAuditEntry` + `AuroraProfiles.audit`, `ProfileBankPolicy` + `AuroraProfiles.bankPolicy()`,
  `CoopInviteInfo` now carries the profile name and type (the Build 52 constructor is kept), archive fields in
  `ProfileDetails`, new error codes `SWITCH_COOLDOWN`, `SWITCH_VETOED`, `PROFILE_ARCHIVED` (appended last).
- **Release asset:** every `v26.2-rN` release from this build on carries `sourbyapi-<N>.zip` (binary, sources and
  javadoc jars plus a README). It is a zip, not loose jars, because the Build 51–54 auto-updater takes the first
  `.jar` asset as the server jar.

### 3. SSB-AuroraProfiles addon port

The SuperiorSkyblock addon (separate repository) is ported to the Build 51–55 API: its `types.yml` (classic, ironman
with the island bank denied, stranded, bingo) is registered through `ProfileTypeRegistry`, and the SSB2 island bank
is enforced with `allows(profile, "island-bank")`.

## Known limits

- The audit log is node-local and in-memory paging covers the newest 4096 entries only.
- `/perf multiprofile` ages are this node's view (listings, claims, votes it ran) and reset at restart.
- Profile events are informational and cannot cancel; use a `ProfileSwitchGuard` to refuse a switch.
- MultiProfile distributed mode and the Redis repository stay EXPERIMENTAL and unqualified.
- A switch that rolls back after its target apply started resets a best-effort adapter whose capture failed when the source profile stores no entry for it (review N1: never the target's value); the live value it had before the switch is not recovered.
