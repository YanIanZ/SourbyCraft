## What is in Build 52 — co-op membership (COOP-DESIGN slice 4, G2)

Design: [COOP-DESIGN.md](../awf/multiprofile/COOP-DESIGN.md). **Co-op is off by default**
(`aurora.awf.multiprofile.coop.enabled: false`, RESTART_REQUIRED) and needs MultiProfile enabled and a format-2
store. With co-op off, the behaviour is Build 51's and `/coop` is not registered.

- **Convert a solo profile to co-op.** The conversion is one-way, and only types in `coop.allowed-types` can be
  converted (default `classic`).
- **Invites.** An invite can be created, accepted, declined or cancelled. It expires after
  `coop.invite-expiry-minutes` (default 5), measured on the store clock at commit.
  - At most 64 open invites per profile and 64 per invitee.
  - An invite is accepted only while its inviter is still a member at the same epoch, with the invite
    permission. A removed member's open invites are revoked when that member is removed.
- **Roles.** OWNER, MANAGER and MEMBER have explicit permissions. A MANAGER can cancel only its own invites.
  Owner transfer and kicking the owner are refused (`OWNER_ACTION_REFUSED`).
- **Leave and vote kick.**
  - Electorate: the starter's approval counts when the vote opens. A vote is cancelled when membership changes
    in the same intent (accept or leave) or when its electorate changed. There is at most one undecided vote
    per profile.
  - Timing: the vote expires after `coop.kick-vote.expiry-minutes` (default 10). The kick must commit before
    the vote expires.
  - Two-member inactivity rule: `coop.kick-vote.inactive-days`, default 35.
- **Size cap.** `coop.max-members`, default 5, allowed 2–8. The cap is checked at commit, so two accepts
  racing for the last seat cannot both succeed.
- **Every membership change is a recoverable intent** on FILE and Redis, and it reserves the profile record.
  - Account-side and profile-side membership change together.
  - A removed member's membership epoch is consumed, so rejoining gets a new epoch and can never restore the
    old one.
  - A removal writes a salvage record marked UNAVAILABLE. Salvage delivery comes in Build 54.
- **Online rule.** A leave or kick is refused with `MEMBER_ONLINE` only when the target's active profile is that
  co-op. In Build 52 only the owner can be active in a co-op (`COOP_SWITCH_UNAVAILABLE` for other members until
  Build 53), so in practice members can leave or be kicked while online.
- **OD-1, one node per co-op.** A membership change on a profile whose claim is held by another node is refused
  with `WRONG_NODE`. A kicked member's session on another node is never taken over (`OWNERSHIP_CONFLICT`).
- **Store level.** The first co-op commit durably raises the store marker to schema 2, minimum build 52.
  - Build 51 then refuses the store at startup. The updater refuses to install or restore anything below the
    level the store requires.
  - A store that never used co-op stays at Build 51 level.
  - FILE keeps a never-backwards store clock (`clock.awfc`), so turning the wall clock back after a restart
    cannot revive an expired invite.
- **API (binary compatible).** New: `CoopRole`, `CoopMemberInfo`, `CoopInviteInfo` and `CoopInviteState`,
  `CoopKickVoteInfo` and `CoopKickVoteState`, `CoopDetails`, `CoopPage`, plus 14 `AuroraProfiles` co-op
  methods. 18 `ProfileErrorCode` values are appended.
  - Events `CoopMemberJoinEvent`, `CoopMemberLeaveEvent` (LEFT/KICKED) and `CoopInviteEvent` are async. They
    fire only after a durable commit, on `SourbyCraft-AWF-coop-events`, from a bounded queue (256, a drop is
    logged).
- **Commands.**
  - `/coop <info|convert|invite|invites|accept|decline|cancel|leave|kick|vote|members|label>` needs
    `sourbycraft.coop.use`. A player sees only co-ops they are a member of.
  - `/awf multiprofile coop …` acts for a named player and needs `sourbycraft.command.awf.admin` for changes.
  - If another plugin already owns `/coop`, only `sourbycraft:coop` is registered, with an INFO naming the
    owner.

## Owner test cases

The test sources were written by agents and **never run by them**. CI runs them on push:
- `CoopMembershipEngineTest`, `CoopMembershipRulesTest`, `CoopMembershipFileTest`, `CoopMembershipRedisTest`
  (the Redis tests skip without `redis-server`)
- the updated `CoopFormat2RecordsTest`

Case names follow COOP-DESIGN §10 slice 4. Manual cases:
- **TO-B52-01:** with co-op off, behaviour is identical to Build 51 and no `/coop` is registered. A skyblock
  plugin's `/coop` keeps working.
- **TO-B52-02:** convert, invite, accept, decline and cancel with two real clients. Check invite expiry.
- **TO-B52-03:** a vote kick with 3 members, and with 2 members under the inactivity rule. A member leaves
  while online in another profile.
- **TO-B52-04:** two accepts race for the last seat, and only one succeeds.
- **TO-B52-05:** kill -9 during an accept and during a kick, restart, and confirm the intent is recovered.
- **TO-B52-06:** after the first co-op commit, the Build 51 jar refuses the store and the updater refuses
  downgrading to 51.
- **TO-B52-07:** Redis variant of TO-B52-02 to TO-B52-05, with `wait-for-aof` on.

## Known limits

- Members cannot switch into, or play, a co-op profile they do not own yet. That comes in Build 53, together
  with per-member snapshots and login restore.
- No bank, collections or salvage delivery yet (Build 54). No audit or type rules yet (Build 55).
- Votes whose electorate changed are closed lazily by the next vote operation, apart from those cancelled by
  accept or leave.
- The open gates from Build 50 and Build 51 are unchanged.
