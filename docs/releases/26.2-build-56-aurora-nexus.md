## What is in Build 56

Both keys are RESTART_REQUIRED and **off by default**; with the defaults the server behaves as Build 55.1 (owner
decision OD-1: one node per co-op). No record type, store level, Lua script or fence changes.

### 1. Co-op members on different nodes (B2)

See [DISTRIBUTED-OWNERSHIP.md](../awf/multiprofile/DISTRIBUTED-OWNERSHIP.md#co-op-across-nodes-build-56-coopcross-node)
and [CONFIGURATION.md](../awf/multiprofile/CONFIGURATION.md#build-56-co-op-across-nodes).

- **The problem.** Since Build 53 the node claim on a profile marks "the node that plays the co-op" (OD-1): while any
  member of a co-op is on the island, the others cannot join the lobby (`OWNERSHIP_CONFLICT` on the node claim, then
  `WRONG_NODE`), and the reverse. On a Lobby + Island pair the only correct configuration was `coop.enabled: false`
  (Build 55.1 notes, "Not changed").
- **What the node claim is for on a format-2 store.** No gameplay write carries it: a member's save, quit and login
  initialisation are fenced by that member's own session claim `Q` plus the stream's revisions
  (`CoopWriteGuard.memberSave`); bank, collection, membership and label changes by the profile transaction claim `P`,
  the actor's `Q` and revision CAS (`STALE_STATE`), with `P` strict across nodes (`OWNERSHIP_CONFLICT`, nothing
  written, the caller retries). The node claim's remaining job is to mark the node that hosts the profile's bound
  worlds.
- **New key `aurora.awf.multiprofile.coop.cross-node`** (default `false` = OD-1): members of one co-op may be on
  different nodes at once. Needs `mode: distributed` and `repository: redis`; the server refuses to start otherwise
  (the FILE repository compares revisions in one process and cannot fence another node).
- **New key `aurora.awf.multiprofile.coop.world-host`** (default `true`, read with `cross-node: true` only):
  - `true`: a **world host** (the island). Takes the node claim and behaves exactly as Build 55.1; a second world host
    of the same co-op is still refused `WRONG_NODE` on join, switch and every co-op operation. A co-op's bound world
    is hosted by one node; there is no routing and no world replication.
  - `false`: a **satellite** (the spawn/lobby node). Takes no node claim on any profile (the session is recorded
    without one, so the quit, lockstep and shutdown captures still run), never prepares, loads or creates a bound world
    (the world port is the no-op one, `prepareActive` returns at once), and refuses nothing as `WRONG_NODE`: a member
    joins with their committed head restored and plays their own stream; bank, collections, invites, accepts and label
    run under `P` and CAS. Needs `switching.enabled: false` (a switch takes the node claim and prepares worlds), and
    `cross-node: true` (`world-host: false` alone is refused at start). Set `isolation.location: false` there.
- **Safety properties kept** (every one is a Build 53–55.1 fence, unchanged): per-member streams and capture tickets
  (`Q`, `A`, `M`, `R`), exactly-once salvage and bank receipts (`P`, `S` CAS, permanent receipts), no duplication (the
  login gate keeps a node's vanilla playerdata out of every save; a refused posting writes nothing).
- **New refusals.** A leave or kick of a member who plays the co-op on the *other* node is `MEMBER_ONLINE` from either
  side (the satellite cannot switch them out, the island cannot take their `Q`); once they quit, the removal repoints
  them as Build 53 does. An operator lock (`/awf multiprofile lock`) of a profile a member has active on another node
  is refused `OWNERSHIP_CONFLICT` naming that node (the satellite holds no node claim for the old check to see);
  archive and delete already refuse on the members' accounts.
- **Start-up:** one INFO names the node's role; the Build 51 WARN that distributed mode is unqualified stays.

### Not changed

- No proxy handoff transport, no routing of players, no live-state transfer: a join restores the last committed head
  (Build 53); the Build 55.1 handoff wait covers the `/server` switch.
- Switch cooldown and `/perf multiprofile` stay per node.
- The pre-Build 56 refusal shapes with `cross-node: false`, including the handoff wait on a node claim other members
  hold (that wait never ends in an admission while they play; it is the OD-1 refusal).

## Owner test cases

The test sources were written by agents and **never run by them**. CI runs them on push:
- `CoopCrossNodeRedisTest` (two engines on one Redis, island = world host, spawn = satellite: a member on each node at
  once with independent streams and the island's claim untouched; a bank posting from each node with conservation,
  `P` serialisation and a retry; invite accepted on the spawn node; leave/kick of a member on the other node
  `MEMBER_ONLINE`; operator lock refused naming the node; the default keeping `WRONG_NODE`). Needs `redis-server`.
- `ProfileSettingsBuild56Test` (both keys: defaults, old constructor, parsing, fallback, AuroraKeys rows; the start-up
  refusals: FILE repository, standalone mode, satellite with switching on, `world-host: false` without cross-node).

Manual cases (two SourbyCraft nodes behind Velocity, `mode: distributed`, Redis repository, `coop.enabled: true`,
`login.authoritative: true`, `handoff-wait-ms: 5000` on both; island `cross-node: true`; spawn `cross-node: true`,
`world-host: false`, `switching.enabled: false`, `isolation.location: false`, `preserve-unregistered: [economy]`):
- **TO-B56-01:** two members of one co-op, one on the island inside the co-op, the other joins the spawn node: admitted
  (no kick), their inventory is their own co-op stream, the island member keeps playing; the spawn member returns to
  the island and arrives with the state they left the spawn node with; the island member's items never change.
- **TO-B56-02:** both members on the island inside the co-op (Build 55 behaviour), then one goes to the spawn node and
  back several times under load: no kick, no duplicated or lost item, `/awf multiprofile status` shows no refused save.
- **TO-B56-03:** `/coop bank deposit` from the spawn node and from the island at the same second, repeatedly: the
  shared balance equals the sum of the accepted deposits; a refused one says `OWNERSHIP_CONFLICT` and nothing changed;
  the audit log shows each posting once.
- **TO-B56-04:** an invite accepted on the spawn node while the owner plays the co-op on the island; the new member
  then switches into the co-op on the island. A kick of a member who is on the spawn node inside the co-op is refused
  `MEMBER_ONLINE`; after they quit it succeeds and their next join restores their solo profile.
- **TO-B56-05:** `/awf multiprofile lock <co-op>` on the island while a member plays it on the spawn node: refused
  naming the spawn node; after they quit: locked.
- **TO-B56-06:** `kill -9` the spawn node while a member plays a co-op there: the island is unaffected; the member's
  rejoin (island or spawn) restores their last committed snapshot after the `Q` TTL; nothing duplicated. Then
  `cross-node: true` with `repository: file` on one node: the server refuses to start naming the key.

## Known limits

- A satellite is trusted to be what its config says: a node that hosts bound worlds but sets `world-host: false` would
  restore members without their world; the engine cannot tell. Keep `world-host` on the island only.
- A member's progress on a satellite since their last save is lost on a crash of that node, exactly as on any node
  (Build 53 autosave lockstep and quit capture); nothing new is at risk, nothing new is protected.
- Cross-node co-op multiplies the surfaces of the unqualified distributed mode (MP-010 never run). It is not
  qualified; the owner cases above are the first evidence.
