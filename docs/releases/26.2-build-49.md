## Theme

Every stability and correctness gate passes on the Build 49 tree. No new features, no
optimization work, no default changed for performance. A change enters 49 only to fix a defect a
gate found.

## Safety order

Correctness > reliability > data safety > stability > compatibility > tail latency > resource
efficiency > startup performance > scalability > throughput (as in the Build 47 doc).

## Stability budget (docs/DEVELOPMENT.md §6)

The release must show: no new cross-region unsafe access; no new world corruption; no
unexplained entity state loss; no protocol breakage; no persistence regression; no
executor/thread leaks; no unbounded queue growth; no sustained heap growth after workload
removal; clean shutdown; repeatable boot.

## Entry criteria

- Build 48 tagged, with its inherited-guard decisions and owned command blocks in the tree (the
  soaks below must exercise that code).
- Release branch name settled (Build 48 decision).
- Access arranged to: real Minecraft clients against Sourby Demo (`online-mode=true` refuses
  headless clients), and a host that can run a 2 h+ soak without dropping. A stability soak does
  not have to be certified; it has to be complete and on the 49 tree.

## Configuration migration (operators) — Build 49 layout

Owner decision 2026-10-22; contract and key tables in [docs/AURORA-CONFIG.md](../AURORA-CONFIG.md) §7.
The first boot of Build 49 on an existing server does this on its own; nothing is deleted:

| What | Before | After the first boot | Copy kept as |
| --- | --- | --- | --- |
| region engine files | `config/canvas-server.yml`, `config/canvas-worlds.yml` | `config/aurora-server.yml`, `config/aurora-worlds.yml` (same values, same per-key comments, new header) | `config/canvas-server.yml.migrated`, `config/canvas-worlds.yml.migrated` |
| `sourbycraft_config/sourbycraft_global_config.toml` | `[ui]`, `[branding]`, `[sourbycraft]`, `[viaversion]`, `[protocollib]`, `[misc.auto_update]`, retired `[perf.smart-swap]` / `[swap.auto-create]`, any Aurora key | `[console]`, `[players]`, `[messages]`, `[plugins.viaversion]`, `[plugins.protocollib]`, `[updater]` with every value kept; retired keys removed; Aurora keys moved to `aurora.toml` | `sourbycraft_global_config.toml.migrated` |
| `sourbycraft_config/aurora.toml` | keys unchanged; `perf.ai.async-pathfinding` if present | `aurora.entity.async-pathfinding`; moved keys arrive documented | `aurora.toml.migrated` (only when it was rewritten) |
| `sourbycraft-security.yml` | unchanged | unchanged (a *fresh* file now carries the header and group comments) | — |

Expected log lines on that boot (one each): `Migrated config/canvas-server.yml -> config/aurora-server.yml (...)`,
`Migrated config/canvas-worlds.yml -> config/aurora-worlds.yml (...)`, `Migrated the configuration files to
the Build 49 layout: N key(s) renamed; ... values unchanged. Previous file kept as ...`. The second boot logs
none of them. If both an old and a new engine file exist (an operator copied one back), the new one is read
and one WARN names the stale file on every load until it is moved. A corrupt old engine file stops the boot
with `could not be migrated ... nothing was written or renamed`: repair or move it, then boot again.

One behaviour note: `aurora.cpu.cores` is read early from `aurora.toml` only (it always was), so a server that had it
only in the global TOML never had the budget applied; after the move it is applied from the second boot on.

Old key names are still read until Build 50 (one WARN per key per load), so a `sourbycraft_config/` the server
cannot write keeps working; the `[viaversion]` / `[protocollib]` tables are also still understood by the
provisioners before the configuration loads. The per-world `canvas-patch.yml` keeps its name. CI's boot
directories still write the old layout and rely on this; updating `.github/workflows/build.yml` to the new
layout is a CI-owner change (not needed for the boots to pass).

*Status 2026-10-25:* Build 49 shipped the files as YAML (PR #53; see [26.2-build-49-release.md](26.2-build-49-release.md)):
the TOML names above are the inputs of the one-time conversion, which keeps the original as `*.toml.migrated`. The
Build 50 candidate (PR #62, `e63f3cc`, unpublished) no longer reads the old key names (`ConfigMigration.stripLegacyNames`,
one WARN per leftover name per load; the provisioners skip a group whose file sets only the pre-49 key) and keeps the
one-time rewrite; its CI boots write the Build 49 YAML layout, with one deliberate pre-49 TOML as the migration input.
`v26.2-r49` and `v26.2-r50` behave as described in this section.

Downgrade to a pre-49 jar: stop, `cp -p config/aurora-server.yml config/canvas-server.yml`,
`cp -p config/aurora-worlds.yml config/canvas-worlds.yml`, restore `*.toml.migrated` over the TOMLs, start.
Values edited after the migration exist only in the new files.
