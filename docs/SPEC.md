# SourbyCraft Modernization Specification

## Status

**Status:** Draft / Implementation Specification
**Project:** SourbyCraft
**Repository:** `YanIanZ/SourbyCraft`
**Target Minecraft Version:** 26.2
**Base:** Paper → CanvasMC → SourbyCraft
**Required Java Version:** Java 25
**Required Production Mode:** No Java preview features
**Primary Goal:** Modernize the entire SourbyCraft-owned codebase and performance architecture for Java 25 while improving CPU efficiency, memory efficiency, scalability, maintainability, and region-thread correctness.

---

# 1. Purpose

This specification defines the technical requirements for the Java 25 and performance modernization of SourbyCraft.

The modernization must improve the server primarily by improving:

* implementation quality
* runtime architecture
* concurrency ownership
* allocation behavior
* CPU efficiency
* memory usage
* I/O handling
* hot-path performance
* maintainability
* profiling capability

It must NOT improve benchmark results by silently reducing configured gameplay workload.

The following principle is mandatory:

> Optimize the engine, not the administrator's configuration.

---

# 2. Hard Requirements

The implementation MUST satisfy all of the following.

## 2.1 Java

* Java 25 is the minimum and only required Java version for this modernization branch.
* All SourbyCraft production Java compilation MUST use Java 25.
* All modules participating in the production build MUST use a Java 25 toolchain.
* `options.release` MUST be 25 where applicable.
* Production runtime MUST NOT require `--enable-preview`.

---

## 2.2 Configuration

The server MUST NOT automatically modify performance-related configuration.

The server MUST NOT implement:

* Auto Config
* Auto Optimize
* Smart Config
* Dynamic Config
* Adaptive Config
* hardware-based config changes
* TPS-based config changes
* MSPT-based config changes
* RAM-based config changes
* player-count-based config changes
* runtime gameplay degradation
* automatic JVM argument modification

Configuration is operator-owned.

---

## 2.3 Runtime Behavior

Performance optimization MUST NOT silently change:

* entity limits
* mob AI frequency
* simulation distance
* view distance
* random tick speed
* chunk behavior
* autosave interval
* packet limits
* compression level
* redstone behavior
* hopper behavior
* world persistence
* plugin event semantics

Any behavior-changing optimization MUST have an explicit administrator-controlled configuration option.

---

# 3. Repository Architecture

The expected dependency hierarchy is:

```text
Minecraft
    ↓
Paper
    ↓
CanvasMC
    ↓
SourbyCraft
```

SourbyCraft MUST remain a downstream implementation and MUST avoid unnecessary invasive modifications to upstream architecture.

Where possible, use:

```text
Upstream class
    ↓
small SourbyCraft hook
    ↓
SourbyCraft-owned service
```

instead of:

```text
Upstream class
    ↓
large embedded SourbyCraft implementation
```

This reduces future rebase cost.

---

# 4. Source of Truth

Generated/materialized upstream sources are NOT the primary source of truth.

Changes must be made through the SourbyCraft patch architecture.

Do not permanently implement changes only inside generated:

```text
paper-server/
paper-api/
canvas-server/
canvas-api/
```

when those directories are regenerated by patch application.

The actual implementation must ultimately exist in SourbyCraft-owned patches or SourbyCraft source directories.

# 6. Package Design

SourbyCraft-owned runtime code SHOULD converge toward the following logical architecture:

```text
dev.iyanz.sourbycraft
├── bootstrap
├── config
├── lifecycle
├── concurrency
├── region
├── world
├── chunk
├── entity
├── network
├── storage
├── scheduler
├── performance
├── diagnostics
├── security
├── command
└── util
```

This is a logical target, not a requirement to perform mass package moves.

Package movement must not create large patch churn without architectural value.

---

# 7. Service Architecture

Large runtime systems SHOULD be represented as lifecycle-owned services.

Preferred example:

```java
public interface SourbyService {

    void start();

    void stop();
}
```

More specialized services may use explicit methods instead.

Service lifecycle MUST be deterministic.

Each service MUST define:

* owner
* initialization point
* shutdown point
* thread-safety contract
* mutable state
* external dependencies

---

# 8. Runtime Context

Avoid uncontrolled global mutable singleton access.

Where practical, create a runtime context containing core SourbyCraft services.

Concept:

```java
public final class SourbyRuntime {

    private final SourbyConfig config;
    private final RuntimeExecutors executors;
    private final DiagnosticsService diagnostics;
    private final StorageService storage;

}
```

This MUST NOT become a service locator where arbitrary code fetches everything globally.

Explicit dependencies remain preferred.

---

# 9. Dependency Injection

Do NOT introduce:

* Spring
* Guice
* CDI
* large DI frameworks

Use explicit constructor-based dependency passing.

Example:

```java
public final class PlayerDataService {

    private final PlayerRepository repository;
    private final RuntimeExecutors executors;

    public PlayerDataService(
            PlayerRepository repository,
            RuntimeExecutors executors
    ) {
        this.repository = repository;
        this.executors = executors;
    }
}
```

---

# 10. Configuration Architecture

Configuration MUST follow:

```text
file
 ↓
parse
 ↓
validate
 ↓
immutable runtime representation
 ↓
runtime services
```

Runtime systems SHOULD NOT continuously query raw config files.

---

# 11. Immutable Config

Prefer immutable configuration data.

Example:

```java
public record NetworkConfig(
        int compressionLevel,
        boolean nativeTransport,
        int packetLimit
) {}
```

Nested configuration SHOULD use immutable structures where practical.

---

# 12. Config Loading

Configuration loading MUST happen through a clearly defined load phase.

Example:

```text
Bootstrap
   ↓
Load configuration
   ↓
Validate
   ↓
Create runtime snapshot
   ↓
Start runtime services
```

Runtime code MUST NOT randomly reload disk configuration without an explicit reload operation.

---

# 13. Config Validation

Invalid values may:

* fail startup
* use a documented runtime fallback
* emit a warning

depending on severity.

Invalid values MUST NOT trigger silent file modification.

Example:

```text
network.compression-level = 900
```

Allowed behavior:

```text
WARN Invalid compression level 900.
Using runtime fallback 6.
Configuration file was not modified.
```

---

# 14. Config Migration

Automatic destructive migration is forbidden.

When a legacy key exists:

```text
old-performance-key = true
```

the server may report:

```text
WARN old-performance-key is deprecated and no longer used.
```

It MUST NOT silently delete or rewrite the operator's file.

---

# 15. Config Access in Hot Paths

Hot paths MUST NOT perform:

* TOML lookup
* YAML lookup
* string key lookup
* reflection-based config access

per tick.

Instead:

```java
if (runtimeConfig.fastEntityTracking()) {
    ...
}
```

using preloaded fields.

---

# 16. Java 25 Language Usage

Modern language features MAY be used where they improve correctness or maintainability.

Preferred candidates:

* records
* sealed types
* pattern matching
* switch expressions
* improved `instanceof`
* immutable collections
* text blocks where suitable

Do NOT rewrite working code merely to appear modern.

---

# 17. Records

Use records for immutable data carriers where identity and mutability are unnecessary.

Good:

```java
public record RegionCoordinate(
        int x,
        int z
) {}
```

Bad candidate:

```java
Entity
Player
Chunk
MutableSchedulerState
```

---

# 18. Sealed Types

Sealed classes/interfaces MAY be used for closed result or state domains.

Example:

```java
public sealed interface LoadResult
        permits LoadSuccess, LoadFailure {
}
```

Use only where the implementation set is intentionally closed.

---

# 19. Optional

`Optional` MUST NOT be blindly introduced into high-frequency internal code.

Prefer nullable internal return values where existing performance-sensitive architecture already uses them safely.

Use Optional mainly for API readability in low-frequency paths.

---

# 20. Streams

Avoid Java Streams inside confirmed hot paths.

Examples where streams SHOULD generally be avoided:

```text
entity tick loops
chunk tick loops
packet loops
collision loops
AI loops
block ticking
scheduler loops
```

Use imperative loops unless benchmarks show no regression.

---

# 21. Lambda Allocation

Check whether lambdas escape or allocate in hot paths.

Do not replace simple loops with callback chains in frequently executed code.

---

# 22. Boxing

Avoid repeated boxing in high-frequency collections.

Example:

Prefer suitable primitive structures over:

```java
Map<Long, ChunkData>
Set<Integer>
List<Long>
```

where boxing is demonstrated to be material.

Use existing dependency ecosystem before introducing new libraries.

---

# 23. Collection Selection

Collection choice MUST be workload-driven.

Consider:

* expected size
* iteration frequency
* lookup frequency
* mutation rate
* concurrency
* memory overhead

Do not default every concurrent structure to `ConcurrentHashMap`.

---

# 24. Collection Capacity

When stable expected capacity is known, pre-size collections.

Example:

```java
new ArrayList<>(expectedEntities);
```

Avoid extreme over-allocation.

---

# 25. Hot Path Definition

The following are considered performance-sensitive until profiling proves otherwise:

* tick loop
* region tick
* entity tick
* mob AI
* chunk lookup
* chunk load/unload
* chunk generation
* chunk sending
* block updates
* redstone
* fluid ticking
* collision
* pathfinding
* packet encode/decode
* entity tracking
* inventory interaction
* hopper processing
* item entities

---

# 26. Hot Path Rules

Hot paths SHOULD avoid:

* reflection
* repeated string creation
* stream pipelines
* unnecessary wrappers
* unnecessary futures
* uncontrolled logging
* repeated config lookup
* temporary collections
* repeated map lookup
* repeated coordinate conversion
* unnecessary synchronization

---

# 27. Threading Model

SourbyCraft inherits region-threaded execution from Canvas/Folia architecture.

Region ownership is authoritative.

Any code mutating region-owned game state MUST execute on the owning region context.

---

# 28. Region-Owned Data

Examples include:

* entities
* blocks
* chunks
* inventory state
* world state
* AI state

Cross-region direct mutation is prohibited.

---

# 29. Cross-Region Operations

Cross-region operations MUST be implemented as explicit scheduler handoffs.

Concept:

```text
Region A
  ↓
create immutable request
  ↓
schedule Region B
  ↓
Region B validates current state
  ↓
Region B applies mutation
```

Do not share mutable entity state across regions.

---

# 30. Async Code

"Asynchronous" MUST NOT be treated as equivalent to "faster".

Async execution is appropriate primarily for:

* I/O
* blocking external calls
* selected independent CPU workloads
* administrative tasks

Game state mutation must return to the correct region scheduler.

---

# 31. Virtual Threads

Virtual threads MAY be used for blocking I/O.

Valid examples:

* HTTP client calls
* database access
* filesystem operations
* metadata fetching
* update checks

Invalid default uses:

* region ticks
* entity ticks
* packet event loops
* CPU-heavy pathfinding
* CPU-heavy world generation
* replacement for region schedulers

---

# 32. Virtual Thread Executor

If virtual threads are introduced, use one lifecycle-owned facility.

Example:

```java
Executors.newVirtualThreadPerTaskExecutor();
```

wrapped by SourbyCraft lifecycle ownership.

It MUST be closed during shutdown.

Do NOT create independent virtual-thread executors throughout the codebase.

---

# 33. Platform Threads

Dedicated platform-thread pools MAY remain appropriate for CPU-bound work.

CPU worker counts MUST be explicit in architecture.

They MUST NOT automatically mutate server config.

---

# 34. Executor Registry

All SourbyCraft-owned executors SHOULD be discoverable through one lifecycle architecture.

Concept:

```java
public final class RuntimeExecutors implements AutoCloseable {

    private final ExecutorService ioExecutor;
    private final ExecutorService cpuExecutor;

}
```

Not every upstream executor needs to be wrapped.

---

# 35. Executor Requirements

Each executor MUST define:

* purpose
* workload type
* queue strategy
* concurrency limit
* lifecycle
* shutdown behavior

---

# 36. Unbounded Queues

New unbounded work queues SHOULD be avoided.

If an unbounded queue is required, its safety rationale MUST be documented.

---

# 37. ForkJoin Common Pool

Do not implicitly use `ForkJoinPool.commonPool()` for SourbyCraft runtime operations.

Forbidden example:

```java
CompletableFuture.supplyAsync(() -> work());
```

Preferred:

```java
CompletableFuture.supplyAsync(
        () -> work(),
        runtimeExecutors.cpuExecutor()
);
```

---

# 38. CompletableFuture

Avoid unnecessary asynchronous chains.

Bad:

```java
CompletableFuture
    .supplyAsync(...)
    .thenApply(...)
    .thenCompose(...)
    .join();
```

when the entire path runs synchronously on the same critical thread.

---

# 39. Blocking

Region threads MUST NOT block waiting for:

* network requests
* database
* disk operations
* external services
* long locks
* `Future.get()`
* `CompletableFuture.join()`

except where upstream architecture explicitly requires a controlled synchronization point.

---

# 40. Locking

Every newly introduced lock MUST have documented ownership.

Prefer:

```text
region ownership
thread confinement
immutable state
message passing
```

before introducing broad synchronization.

---

# 41. Lock Scope

Locks MUST be as narrow as correctness permits.

Do not use a single global lock for unrelated regions.

---

# 42. Deadlock Prevention

Avoid acquiring multiple subsystem locks in inconsistent order.

Where multiple locks are unavoidable, define a strict lock ordering.

---

# 43. ThreadLocal

Every SourbyCraft-owned ThreadLocal MUST be reviewed.

Document:

* stored type
* thread lifetime
* memory retention
* cleanup behavior
* compatibility with region threads
* compatibility with virtual threads

---

# 44. Object Pools

Custom object pooling MUST NOT be assumed faster.

Existing pools MUST be benchmarked against normal allocation.

Remove pools where they:

* increase synchronization
* retain large heaps
* complicate resets
* cause stale state risks
* show no measurable win

---

# 45. Allocation Policy

Primary allocation optimization approach:

1. profile
2. identify dominant allocation source
3. identify root cause
4. reduce unnecessary creation
5. benchmark

Do NOT prematurely optimize every allocation.

---

# 46. Allocation Targets

Prioritize high-frequency allocation sources such as:

* temporary lists
* temporary maps
* block position wrappers
* packet buffers
* tracking collections
* pathfinding objects
* entity query lists
* serialization buffers

---

# 47. Cache Policy

Every new cache MUST define:

```text
Key
Value
Owner
Maximum lifetime
Invalidation
Maximum size or natural bound
Thread ownership
```

No uncontrolled permanent cache.

---

# 48. Cache Invalidation

Correctness beats hit rate.

Never reuse stale world/entity/chunk state simply to improve benchmarks.

---

# 49. Entity Tick Optimization

Entity tick optimization MUST preserve observable semantics unless explicitly configurable.

Evaluate:

* duplicate calculations
* repeated world access
* repeated distance checks
* activation logic
* AI scheduler cost
* collision queries
* tracker updates

---

# 50. AI Optimization

Potential optimization areas:

* GoalSelector iteration
* target scanning
* path recalculation
* sensors
* Brain behaviors
* collision checks
* navigation updates

AI frequency MUST NOT dynamically change based on server lag without explicit operator configuration.

---

# 51. Entity Query Optimization

Avoid full-world or broad-region scans when an indexed or region-local query exists.

Do not create duplicate global entity indices without proving they outperform existing infrastructure.

---

# 52. Item Entities

Profile:

* merging
* pickup detection
* movement
* nearby-item search
* despawning
* metadata updates

Pooling item objects requires benchmark evidence.

---

# 53. Chunk Architecture

Optimize:

* chunk key lookup
* holder lookup
* ticket processing
* player tracking
* load/unload
* generation
* sending
* save scheduling

Avoid duplicate state maps.

---

# 54. Chunk Ownership

Chunk state mutation MUST respect region ownership.

Async jobs may prepare immutable results but MUST hand mutation back to the owning region.

---

# 55. Chunk I/O

Disk I/O SHOULD be separated from latency-critical region execution where supported safely.

Potential steps:

```text
snapshot state
 ↓
serialize
 ↓
I/O executor
 ↓
write
```

Do not move unsafe live mutable objects into async threads.

---

# 56. Chunk Save Semantics

Optimization MUST NOT weaken persistence guarantees.

Configured save behavior remains authoritative.

---

# 57. World Saving

Avoid:

* repeated serialization of unchanged state
* duplicate save requests
* unnecessary immediate flushes

where safe.

---

# 58. Region File Access

Region file access MUST have clearly defined thread and locking semantics.

Do not introduce parallel writes that can corrupt region files.

---

# 59. Redstone

Redstone optimization MUST preserve expected behavior unless the project explicitly exposes an alternative mode.

Profile before redesigning.

---

# 60. Block Entities

High-frequency block entities such as:

* hoppers
* furnaces
* chests
* comparators

SHOULD be profiled separately.

Avoid repeated inventory scans where state is unchanged.

---

# 61. Networking

Network optimization MUST preserve protocol correctness.

Profile:

* encode
* decode
* packet allocation
* compression
* queueing
* flushes
* entity tracking packets
* chunk transmission

---

# 62. Netty Event Loop

Never perform CPU-heavy or blocking work directly on Netty event-loop threads.

Examples prohibited:

* database queries
* filesystem operations
* large compression work outside designed Netty pipeline behavior
* expensive JSON processing
* world operations

---

# 63. Packet Queues

Queues MUST have clear ownership and growth behavior.

Unbounded player packet queues require special justification.

---

# 64. Compression

Compression implementation may be optimized.

Compression configuration MUST remain explicit.

Never automatically change compression level based on:

* CPU load
* TPS
* MSPT
* player count
* bandwidth

---

# 65. Serialization

Optimize copy count.

Avoid chains such as:

```text
object
 ↓
byte[]
 ↓
ByteBuffer
 ↓
new byte[]
 ↓
ByteBuf
```

when fewer copies are safely possible.

---

# 66. Logging

Use parameterized logging.

Bad:

```java
LOGGER.debug("Player " + player + " loaded " + chunks + " chunks");
```

Preferred:

```java
LOGGER.debug(
        "Player {} loaded {} chunks",
        player,
        chunks
);
```

---

# 67. Hot-Path Logging

Debug/trace logs inside hot loops MUST be guarded or eliminated where expensive.

Do not generate diagnostic strings when logs are disabled.

---

# 68. Exception Handling

Exceptions MUST NOT represent normal expected tick-loop control flow.

Repeated caught exceptions are a performance defect until justified.

---

# 69. Reflection

Reflection is acceptable during bootstrap or low-frequency compatibility operations.

Reflection inside tick loops SHOULD be eliminated where practical.

---

# 70. Startup

Startup MUST remain deterministic.

Profile:

* patch/bootstrap
* configuration
* registry
* libraries
* plugin scanning
* world loading

Avoid unnecessary network calls after initial bootstrap.

---

# 71. Shutdown

All SourbyCraft-owned executors and services MUST shut down.

Preferred sequence:

```text
Stop accepting work
 ↓
Stop external services
 ↓
Complete/cancel outstanding operations
 ↓
Flush persistent state
 ↓
Close executors
 ↓
Release resources
```

---

# 72. Shutdown Timeout

Services that can hang indefinitely SHOULD have bounded shutdown behavior.

Do not leave JVM shutdown dependent on stuck custom non-daemon threads.

---

# 73. Performance Measurement

No performance claim without measurement.

Minimum accepted evidence:

* before commit/hash
* after commit/hash
* workload
* Java version
* JVM args
* hardware
* runtime duration
* warmup
* configuration

* loading
* unloading

# 94. Dead Code

# 95. Upstream Duplication

If Canvas or Paper now implements an equivalent SourbyCraft optimization:

---

# 96. Patch Maintenance

Prefer small patches with one responsibility.

Avoid giant patches touching unrelated systems.

---

# 97. Patch Comments

Performance patches SHOULD include comments explaining non-obvious behavior.

Avoid comments that merely restate code.

---

# 98. Public API

Do not expose implementation internals unnecessarily.

Public API additions require:

* clear use case
* stable semantics
* thread-safety documentation

---

# 99. Internal API

Internal packages may change aggressively during modernization.

No backward-compatibility promise is required for internal SourbyCraft classes unless otherwise documented.

---

# 100. Security

Do not weaken:

* packet validation
* packet rate limits
* malformed data protection
* crash guards
* resource exhaustion protections

for benchmark gains.

---

# 101. External I/O

All external HTTP/database/filesystem operations MUST define:

* timeout
* error handling
* cancellation behavior where applicable

No infinite HTTP waits.

---

# 102. HTTP

HTTP operations SHOULD use one shared, lifecycle-managed client where appropriate.

Avoid creating a new client per request.

---

# 103. Database

If database integrations exist:

* use bounded connection pooling
* avoid region-thread blocking
* use parameterized queries
* define timeout behavior

---

# 104. File I/O

Frequent small file operations SHOULD be batched where safe.

Configuration files are not to be rewritten automatically.

---

# 105. Temporary Files

Temporary files MUST be cleaned up deterministically.

---

# 106. Hardware Detection

Hardware detection MAY be used for diagnostics only.

Allowed:

```text
Detected CPU: 8 cores
Detected RAM: 16 GB
```

Not allowed:

```text
Automatically setting region threads to 6.
```

---

# 107. JVM Flags

SourbyCraft MUST NOT rewrite or automatically generate performance JVM flags based on hardware.

Documentation MAY recommend optional JVM flags.

---

# 108. GC

No custom GC configuration should be required for server correctness.

The engine should optimize allocation first.

---

# 109. Resource Efficiency

Performance should be evaluated using efficiency metrics such as:

```text
players / core
players / GB
entities / MSPT
chunks / CPU-second
packets / CPU-second
```

---

# 110. Memory

Prefer reducing:

* duplicate collections
* duplicate cache entries
* retained world references
* unnecessary wrappers
* oversized buffers

---

# 111. Buffers

Buffer reuse is permitted when ownership is clear.

Avoid custom buffer pools where Netty/JVM already provides effective pooling.

---

# 112. False Sharing

If profiling identifies cache-line contention in high-frequency counters/state, padding or structural separation MAY be considered.

Do not add manual padding speculatively.

---

# 113. Volatile

Do not mark fields `volatile` without a clear memory-ordering requirement.

Volatile reads in hot paths have cost.

---

# 114. Atomic Types

Do not replace all synchronization with atomics.

Use atomic operations only when they accurately model ownership and concurrency.

---

# 115. Copy-on-Write

Avoid copy-on-write collections for high-write runtime paths.

They may remain suitable for rare-write listener/configuration sets.

---

# 116. String Handling

Avoid repeated creation of equivalent strings in hot paths.

Do not introduce manual string interning without evidence.

---

# 117. Key Representation

For frequently used world/chunk/entity keys, prefer efficient stable representations.

Avoid repeatedly constructing compound strings such as:

```text
world:x:z
```

for hot-path map keys.

---

# 118. Coordinate Packing

Existing packed integer/long coordinate representations SHOULD be preferred where safe.

Do not create duplicate coordinate encoding schemes.

---

# 119. Time Measurement

Use monotonic time for durations.

Prefer:

```java
System.nanoTime()
```

for elapsed-time measurements.

Do not use wall-clock time for MSPT measurement.

---

# 120. Random Number Generation

Use existing thread/region-appropriate RNG architecture.

Do not create a new `Random` per tick.

---

# 121. Sorting

Avoid sorting large collections every tick unless ordering is semantically necessary.

---

# 122. Event Dispatch

Profile expensive event paths.

Do NOT skip Bukkit/Paper events simply for performance unless SourbyCraft explicitly documents a compatibility-breaking mode.

---

# 123. Plugin Calls

Plugin callbacks may be expensive but remain part of expected server semantics.

Diagnostics SHOULD distinguish server engine time from plugin time where possible.

---

# 124. Scheduler

Avoid unnecessary scheduler wrapper allocations.

Region scheduler ownership remains authoritative.

---

# 125. Scheduled Tasks

Repeated scheduled tasks SHOULD avoid:

* unnecessary object creation
* accidental capture of large objects
* permanent references after cancellation

---

# 126. Cancellation

Cancelled tasks MUST become eligible for garbage collection.

---

# 127. Player Lifecycle

On disconnect, SourbyCraft-specific state associated with the player MUST be removed unless intentionally persisted.

---

# 128. World Lifecycle

World-specific services/state MUST be disposed when worlds unload.

---

# 129. Chunk Lifecycle

Chunk-local caches MUST NOT retain unloaded chunks indefinitely.

---

# 130. Region Lifecycle

Region-local state MUST have a defined cleanup lifecycle.

---

# 135. Prohibited Implementation Patterns

Do NOT introduce systems equivalent to:

```java
if (mspt > 45) {
    lowerEntityLimit();
}
```

Do NOT:

```java
if (Runtime.getRuntime().maxMemory() < threshold) {
    rewriteConfig();
}
```

Do NOT:

```java
if (onlinePlayers > 100) {
    decreaseViewDistance();
}
```

Do NOT:

```java
if (cpuUsage > 90) {
    disableMobAI();
}
```

# 136. Allowed Adaptive Internals

Internal algorithms MAY adapt when this does not alter configured server semantics.

Example acceptable behavior:

* dynamically resizing an internal temporary buffer
* changing an internal batching strategy
* selecting a more efficient algorithm based on collection size
* internal backpressure for non-gameplay external I/O

Example unacceptable behavior:

* reducing configured gameplay workload

---

# 137. Backpressure

External asynchronous services SHOULD implement backpressure where queue growth could become unsafe.

Backpressure MUST NOT freeze region threads.

---

# 138. Failure Isolation

Failure in an optional SourbyCraft diagnostic or external service MUST NOT crash unrelated game regions unless data integrity/security requires shutdown.

---

# 139. Error Logging

Repeated identical failures SHOULD be rate-limited where appropriate to avoid log-induced overload.

Do not hide serious errors.

---

# 140. Compatibility

Modernization must preserve intended compatibility with:

* Bukkit API
* Paper API
* Canvas functionality
* supported plugins
* SourbyCraft API

unless explicitly documented otherwise.

---

# 141. Minecraft Semantics

Performance changes MUST preserve vanilla gameplay semantics where SourbyCraft has not explicitly defined different behavior.

---

# 142. Rebase Friendliness

When changing upstream classes:

* minimize modified lines
* avoid unrelated formatting
* avoid massive renames
* keep integration hooks narrow

---

# 143. Formatting

Do not perform repository-wide formatting as part of performance PRs.

Formatting noise increases patch conflicts.

---

# 144. Comments

Do not retain outdated performance claims.

Example:

```text
// 50% faster
```

must have evidence or be removed.

---

# 145. Magic Numbers

Performance constants MUST have meaningful names or explanation.

Bad:

```java
if (size > 73) {
```

Preferred:

```java
if (size > LINEAR_SCAN_THRESHOLD) {
```

when the threshold has justification.

---

# 146. Performance Thresholds

Algorithm-switch thresholds SHOULD be benchmark-derived.

---

# 147. Feature Flags

Temporary feature flags MAY be used during migration.

Permanent feature flags should exist only where operators genuinely need behavioral choice.

---

# 148. Experimental Optimizations

Experimental optimizations MUST default off unless proven safe and mature.

They MUST NOT silently enable themselves based on hardware.

---

# 149. Removal Criteria

An existing optimization may be removed if:

* upstream supersedes it
* benchmark shows no benefit
* it introduces excessive complexity
* it increases memory disproportionately
* it violates region safety

# 150. Acceptance Criteria

The modernization is complete when all of these are true:

* Java 25 is consistently used.
* Production does not require preview features.
* SourbyCraft-owned services have explicit lifecycle ownership.
* Config files are not automatically rewritten.
* No automatic server performance configuration exists.
* No TPS/MSPT-driven gameplay degradation exists.
* Executor ownership is documented.
* Blocking I/O is removed from critical region threads where practical.
* Common-pool async usage has been audited.
* ThreadLocal usage has been audited.
* Custom object pools have been audited.
* Allocation hotspots have been profiled.
* Entity/AI hot paths have been profiled.
* Chunk/world hot paths have been profiled.
* Network hot paths have been profiled.
* Memory leaks have been tested.
* Region-thread correctness remains intact.
* World persistence remains correct.
* Boot and shutdown tests pass.
* Plugin compatibility is preserved.
* Performance benchmark methodology exists.
* No unexplained relevant benchmark regression exceeds the accepted threshold.
* At least one significant workload demonstrates measurable performance/resource improvement.
* Legacy patches have been reviewed for removal.
* Documentation is updated.

---

# 151. Final Engineering Principle

Every optimization should answer:

```text
What is expensive?
Why is it expensive?
How was it measured?
What changed?
Why is the new implementation safe?
How much faster or more efficient is it?
What new complexity does it introduce?
```

If those questions cannot be answered, the optimization is not ready to merge.

The final SourbyCraft architecture should be:

```text
Java 25
+
Canvas region threading
+
explicit ownership
+
immutable configuration
+
low contention
+
low allocation
+
efficient I/O
+
measurable optimization
+
small downstream patches
+
predictable server behavior
```

and never:

```text
lag detected
      ↓
silently change config
      ↓
reduce gameplay workload
      ↓
claim performance improvement
```

SourbyCraft performance improvements must originate from better engineering, not hidden configuration changes.
