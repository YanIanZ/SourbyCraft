# Region-threaded commands — /tp, /clone, /summon

## Scope and status

- Branch `26.2`, Build 48. Read 2026-10-21 from the materialized sources at `paperRef` 9240f586 with
  the tree's feature patches applied, plus the SourbyCraft-owned engine sources. Nothing here was
  booted; every statement is from reading code and is marked LIVE (current code) or planned.
- Source of truth for the guard list: `docs/architecture/inherited-guards.md`. This guide covers the
  commands whose ledger row has kind `REROUTED`. There are exactly three such commands in the ledger:
  `/tp` (`TeleportCommand#1`), `/clone` (`CloneCommands#1`), `/summon` (`SummonCommand#1`). The other
  `REROUTED` ledger rows are not commands (network `Connection`, `ChunkMap`, entity/player internals,
  the scheduler, spark); they are out of scope here.
- Command sources are under `sourbycraft-server/src/minecraft/java/net/minecraft/server/commands/`.
  This is a generated working tree (regenerated by `applyAllPatches`); do not edit it. The three
  commands are inherited Folia/Canvas reroutes. SourbyCraft's only owned addition in this area is the
  command-block scope check (`CommandBlockRegions.requireOwned*`, feature patch 0055), which is a no-op
  for players, console and plugins.

What "REROUTED" means here: the command does not perform the work inline on the sender's thread.
Instead it schedules the work on the region (or entity scheduler) that owns the target and returns
immediately. The real move/clone/spawn completes later. A chained command, `execute store result`,
a comparator on a command block, or a function that runs right after therefore sees the state
*before* the work is done.

## /tp (TeleportCommand)

Register path: `sourbycraft-server/src/minecraft/java/net/minecraft/server/commands/TeleportCommand.java:37-148`.
`/tp` is an alias redirect to `/teleport` (`:148`). There are two execution shapes:

- `tp <target> <destination entity>` runs `teleportToEntity` (`:151-168`).
- `tp <targets> <location> [...]` runs `teleportToPos` (`:170-211`), which loops into `performTeleport`
  (`:224-281`).

### What happens on SourbyCraft versus vanilla

Both shapes schedule the teleport and return; they do not move the entity inline.

- To an entity: `teleportToEntity` calls `io.papermc.paper.threadedregions.TeleportUtils.teleport(...)`
  with `Entity.TELEPORT_FLAG_LOAD_CHUNK` and cause `COMMAND` (`:153`). `TeleportUtils` reads the
  destination's location on the destination entity's region, then schedules `teleportAsync` on the
  victim's region (`sourbycraft-server/src/minecraft/java/io/papermc/paper/threadedregions/TeleportUtils.java:66-76`, `:35-62`).
- To coordinates: `performTeleport` is guarded by `if (true) { ... return; }` (`:251`). It schedules
  `stopRiding()` then `teleportAsync(...)` with `TELEPORT_FLAG_LOAD_CHUNK | TELEPORT_FLAG_TELEPORT_PASSENGERS`
  and cause `COMMAND` on the victim's own entity scheduler via
  `victim.getBukkitEntity().taskScheduler.scheduleOrExecute(...)` (`:255-263`). The synchronous
  `victim.teleportTo(...)` path below (`:267-280`) is dead code.

### Returns before completion, result and feedback

Yes. Both shapes send the success message and return `entities.size()` immediately (`:156-165`, `:167`;
`:190-208`, `:210`). The number is the count of targets, not a teleport that has already happened.

- On vanilla the count is also `entities.size()`, but the move is synchronous at that point.
- `scheduleOrExecute` runs the callback inline only when the current thread already owns the victim,
  otherwise it schedules for the next tick (`sourbycraft-server/src/minecraft/java/io/papermc/paper/threadedregions/EntityScheduler.java:167-185`).
  Either way the command returns before the move unless it happened to already own the entity.
- The synchronous position check (`Level.isInSpawnableBounds`, `TeleportCommand.java:236-239`) still
  runs inline, so an out-of-bounds coordinate still fails immediately with
  `commands.teleport.invalidPosition`.

### Cross-region target

Handled by the reroute. The victim's teleport is scheduled on the victim's own entity scheduler, and
`teleportAsync` performs the region change itself, so a target in another region (or another dimension)
is supported; the move lands later on the owning region's thread.

### Unloaded target chunk

The teleport is issued with `Entity.TELEPORT_FLAG_LOAD_CHUNK` (`:153`, `:260`), so the destination
chunk is loaded/generated by the teleport path.

### Discrepancy from vanilla (LIVE)

The `facing` look-at is dropped. `performTeleport` receives a `lookAt` argument (the `facing entity` /
`facing <coords>` subcommands, `:90-138`), and vanilla applies it with `lookAt.perform(source, victim)`
inside the synchronous `teleportTo` branch (`:268-270`). On SourbyCraft that branch is unreachable, so
`/tp ... facing ...` does not rotate the victim toward the target. The rotation arguments (`rotation`
and default rotations) are still honoured because they feed `newYRot`/`newXRot` into `teleportAsync`
(`:253-262`).

## /clone (CloneCommands)

Register path: `sourbycraft-server/src/minecraft/java/net/minecraft/server/commands/CloneCommands.java:47-165`.
The clone body is `clone(...)` (`:231-550`). SourbyCraft-owned command-block check:
`CommandBlockRegions.requireOwned(...)` for source and destination (`:266-269`), a no-op outside a
command-block scope (`sourbycraft-server/src/main/java/dev/iyanz/sourbycraft/commandblock/CommandBlockRegions.java:45-47`).

### What happens on SourbyCraft versus vanilla

Guarded by `if (true) { ... return 1; }` (`:271`, `:437`). The inherited Canvas implementation works
as a snapshot copy-paste:

1. Schedule onto the source region to collect a snapshot of blocks, block entities and block ticks
   (`fromDimension.canvas$loadOrRunAtChunksAsync(...)`, `:281-286`; collection loop `:314-322`). In
   `MOVE` mode the source blocks are cleared to air on that same pass (`:331-341`).
2. Schedule onto the destination region to place barriers, set states, restore block entities, update
   neighbours and re-schedule ticks (`toDimension.canvas$loadOrRunAtChunksAsync(...)`, `:345-350`;
   apply loop `:363-427`).
3. Send `commands.clone.success` with the real count from the destination region's thread (`:429`).

The synchronous vanilla block-by-block path below (`:440-549`) is dead code.

### Returns before completion, result and feedback

Yes. The command returns `1` immediately (`:437`), before any block is placed. The success message
with the actual block count arrives later, from the destination region's thread (`:429`).

- On vanilla the command returns `count` (`:549`) synchronously, or throws
  `commands.clone.failed` when `count == 0` (`:543-545`).
- On SourbyCraft the return value is always `1`, not the block count, and the `commands.clone.failed`
  error is never raised: the async lambda just reports success with whatever count it computed, even 0.
- Consequently `execute store result run clone ...` stores `1`, and a conditional (`execute if ...`
  on `success`) or a comparator reads success as if the clone were already complete.

### Cross-region target

Supported. Source and destination are each scheduled on their own region (and can be different
dimensions; the two `ServerLevel`s are captured separately, `:246-247`, `:281`, `:345`). The snapshot
is taken where the source lives and applied where the destination lives.

### Unloaded source or destination chunk

There is a synchronous loaded-chunk check before scheduling:
`if (!fromDimension.hasChunksAt(startPos, endPos) || !toDimension.hasChunksAt(destPos, destEndPos))
throw BlockPosArgument.ERROR_NOT_LOADED.create();` (`:258-260`). So unloaded source or destination
chunks fail the command immediately with the vanilla "not loaded" error. After that check passes,
`canvas$loadOrRunAtChunksAsync` loads any not-yet-loaded chunks itself
(`sourbycraft-server/src/minecraft/java/net/minecraft/world/level/Level.java:1373-1398`,
`:1400-1422`), so the snapshot/apply can proceed on the region.

## /summon (SummonCommand)

Register path: `sourbycraft-server/src/minecraft/java/net/minecraft/server/commands/SummonCommand.java:37-75`.
`spawnEntity` (`:115-121`) calls `createEntity` (`:77-113`).

### What happens on SourbyCraft versus vanilla

`createEntity` creates the entity object inline (`EntityType.loadEntityRecursive`, `:92`), then queues
the actual add-to-world with
`AbstractCommandExecution.executeAtPos(() -> { finalizeSpawn(...); level.tryAddFreshEntityWithPassengers(...); }, pos, level, source)`
(`:101-106`). `executeAtPos` runs that block on the region that owns the target chunk coordinates via
`RegionizedServer.getInstance().taskQueue.queueOrExecuteTickTask(...)` and returns `SINGLE_SUCCESS`
immediately (`sourbycraft-server/src/minecraft/java/dev/iyanz/aurora/engine/threadedregions/commands/AbstractCommandExecution.java:119-132`).

### Returns before completion, result and feedback

Partly. The entity object is created inline, but the add-to-world (finalize + `tryAddFreshEntityWithPassengers`)
is queued and the command returns `Command.SINGLE_SUCCESS` (`1`) and sends
`commands.summon.success` immediately (`:119-120`). A function or command chain that runs right after
does not yet see the entity in the world (for example an `execute ... run` that selects the new entity
or reads `@e` by tag).

- Vanilla performs `tryAddFreshEntityWithPassengers` synchronously before returning.

### Duplicate UUID (LIVE difference)

The duplicate-UUID error is disabled. `if (false) { throw ERROR_DUPLICATE_UUID.create(); } else {
return entity; }` (`:108-111`) always returns the entity. So a `/summon` that would collide on UUID
reports success and returns `1` instead of failing with `commands.summon.failed.uuid`. The code
comment notes the duplicate is absorbed by `EntityLookup` during the add (`:106`), so the entity is
simply not added again. This is an inherited Folia change, not a SourbyCraft addition.

### Cross-region target

Supported. `executeAtPos` queues the add onto the region that owns the target position
(`queueOrExecuteTickTask`, `AbstractCommandExecution.java:119-131`; runs inline only if the caller
already owns those chunk coordinates, `sourbycraft-server/src/minecraft/java/io/papermc/paper/threadedregions/RegionizedTaskQueue.java:80-88`).
The entity is added on that region's thread.

### Unloaded target chunk

Unlike `/clone`, `/summon` does not call a chunk-loading helper. `executeAtPos` uses
`queueOrExecuteTickTask`, which schedules onto the region's task queue and does not load the chunk
(`RegionizedTaskQueue.java:80-88`). The out-of-bounds position check is still inline
(`SummonCommand.java:80-83`, `commands.summon.invalidPosition`). The entity is created and handed to the
owning region, but no explicit chunk load is requested here; the downstream behaviour of adding an
entity into an unloaded chunk is not verified in this reading (see Unverified).

## Practical advice

- Do not rely on `execute store result` for a rerouted command. `store result run clone ...` stores
  `1`, not the block count (`CloneCommands.java:437`). `/tp` stores the target count before the move,
  and `/summon` stores `1` before the add. Read the resulting world/entity state instead of the result.
- Do not chain a rerouted command's success into a function that assumes the work is already done.
  After `execute ... run tp ...`, the victim has not yet moved; after `run clone ...`, no block has
  been placed; after `run summon ...`, the entity is not yet in the world. Insert a delay or check the
  resulting state (for example `execute if block`/`if entity` after the delayed work, or a scheduled
  function that runs a tick later) before acting on the outcome.
- `execute if|unless success` and command-block comparators measure the command *return*, which for
  these commands reports "scheduled", not "done". A conditional block chained off a rerouted `/clone`
  will fire even if the clone later produces zero blocks.
- `/clone` still fails fast on unloaded chunks (`commands.clone.failed`-style "not loaded", `:258-260`);
  it is the one of the three that both checks and then loads chunks itself. `/tp` loads the destination
  chunk via `TELEPORT_FLAG_LOAD_CHUNK`. `/summon` requests no chunk load — pre-load the area if you
  need the mob to tick immediately.
- `/tp ... facing ...` does not rotate the victim on this engine (`TeleportCommand.java:251-270`). Use
  explicit `rotation` coordinates instead if facing matters.
- A duplicate-UUID `/summon` silently reports success instead of failing
  (`SummonCommand.java:108-111`); do not use the command's failure to detect that the entity was not
  created.
- These behaviours are inherited Folia/Canvas reroutes, not SourbyCraft policy. They apply to every
  command source (player, console, command block); command blocks additionally narrow block targets to
  the block's own region — see `docs/architecture/command-blocks.md`.

- The claim that a duplicate-UUID `/summon`'s entity is simply "not added again" rests on the code

  path itself was not read. Marked **UNVERIFIED**.
- Whether `stopRiding()` before `teleportAsync` in `/tp` (`TeleportCommand.java:256`) has any
