# Login guards inherited from the Folia baseline

Status: **documentation only**, written 2026-10-20 against the current branch for audit row
SEC-11 (`docs/audits/2026-10-14-system-audit.md` §3, marked PLAUSIBLE there; this page is the
verification). SourbyCraft changes none of this behaviour today, exposes no setting for it, and
the connection-rate limit the audit proposed is **not built and not planned until accepted**.
Everything below is in the inherited engine baseline (`sourbycraft-server/minecraft-patches/sources`,
formerly Folia/Canvas), so changing any of it means a new feature patch under
`sourbycraft-server/minecraft-patches/features/`, not an edit to these files (AGENTS.md, *Patch
application*).

## 1. What Paper does

Paper (the pinned `paperRef`) has three guards on the login path:

| Guard | Where in Paper | Behaviour |
|---|---|---|
| Join buffering | `net.minecraft.network.Connection#tick`, `MAX_PER_TICK` = `misc.max-joins-per-tick` (`paper-global.yml`, default 5: `paper-server/src/main/java/io/papermc/paper/configuration/GlobalConfiguration.java:321`) | At most N login listeners in state `VERIFYING` are ticked per server tick; `joinAttemptsThisTick` resets each tick |
| Synchronous pre-login | `ServerLoginPacketListenerImpl`, after `AsyncPlayerPreLoginEvent` | If a `PlayerPreLoginEvent` listener is registered, the (deprecated) sync event is fired on the main thread and can disallow the login |
| Duplicate profile | `PlayerList#disconnectAllPlayersWithProfile`, login state `WAITING_FOR_DUPE_DISCONNECT` | An online player with the same profile is disconnected and the new login waits for that disconnect before it finishes |

## 2. What the region-threading baseline does instead

Verified in the patch files and in the materialized sources they produce
(`sourbycraft-server/src/minecraft/java/...`, regenerated by `applyAllPatches`).

### 2.1 Join buffering: removed, `max-joins-per-tick` re-purposed

- `minecraft-patches/sources/net/minecraft/network/Connection.java.patch` replaces Paper's gate
  with `if (true) { // Folia - region threading` (materialized `Connection.java:681`) and comments
  out the per-tick reset of `joinAttemptsThisTick` under `// Folia start - this is broken`
  (`:644-651`). `MAX_PER_TICK` is still declared (`:640`) but no longer guards anything.
  **Effect:** there is no per-tick cap on how many verifying logins proceed; each connection ticks
  on its own thread schedule.
- `.../server/network/ServerLoginPacketListenerImpl.java.patch` gates `VERIFYING` on
  `PlayerList#pushPendingJoin(name, uuid, connection)` instead (materialized `:98`); when it returns
  `false` the listener rewinds its tick counter (`--this.tick`) and retries next tick.
- `.../server/players/PlayerList.java.patch` adds `pushPendingJoin` (`// Folia start - max
  concurrent login`). It refuses a new login when the number of connections registered in
  `connectionById` that are **not yet** in the game state (`connectionById.size() - loggedInCount`)
  is `>= GlobalConfiguration.get().misc.maxJoinsPerTick`.
  **Effect:** `max-joins-per-tick` means *maximum concurrent pending logins* here, not *logins
  completed per tick* as Paper documents it. With the default 5, a sixth simultaneous login waits a
  tick and retries; once a login reaches the game listener it stops counting. The value is read on
  every attempt from the loaded Paper global configuration.

### 2.2 Synchronous `PlayerPreLoginEvent`: never fired

`ServerLoginPacketListenerImpl.java.patch` turns the check into
`if (false && PlayerPreLoginEvent.getHandlerList().getRegisteredListeners().length != 0)`
(materialized `:353`). `AsyncPlayerPreLoginEvent` still fires; `PlayerLoginEvent` still fires
(SourbyCraft's own `maxplayers/MaxPlayersBypass.java:69` relies on it).
**Plugin consequence:** a plugin that only listens to the deprecated sync event gets no callback and
nothing warns about it. That includes legacy plugins loaded through the Aurora Bridge: the bridge
routes scheduler work, it does not resurrect an event the server never calls.

### 2.3 Duplicate profile: same outcome, different mechanism

- Paper's path is disabled: `waitForDisconnection = false && playerList.disconnectAllPlayersWithProfile(profile)`
  (materialized `ServerLoginPacketListenerImpl.java:239`), and `PlayerList.java.patch` deletes the
  disconnect loop inside `disconnectAllPlayersWithProfile` (`// Folia - region threading`), so
  `WAITING_FOR_DUPE_DISCONNECT` is never entered.
- Replacement: `pushPendingJoin` keeps `connectionByName` / `connectionById` under
  `connectionsStateLock`. A conflicting name or UUID that is still connected gets
  `disconnectSafely(multiplayer.disconnect.duplicate_login)` and the new login is refused for that
  tick; it retries until `removeConnection` has dropped the old entry. The check therefore covers
  every connection from `VERIFYING` onward, not only players already in game.

## 3. What this means in practice

- **No join-rate throttle exists.** Bursts of logins are bounded only by the concurrent-pending cap
  above (default 5) and by the network layer. `sourbycraft-security.yml` has no login, join or
  handshake key (checked 2026-10-20: `rg -i 'login|join|connection|handshake'` finds nothing), so
  SourbyCraft adds nothing here. A connection-rate limit was proposed in the audit; it is an owner
  decision and no code exists for it.
- **`max-joins-per-tick` does not do what the Paper docs say.** Operators tuning it for a login
  burst are changing the concurrent-pending cap. Whether that cap deserves its own key is an owner
  decision; either way it would be a feature patch over the baseline.
- **Plugin authors:** use `AsyncPlayerPreLoginEvent` or `PlayerLoginEvent`; the sync
  `PlayerPreLoginEvent` is dead on this server.
- Nothing on this page is LIVE or RESTART_REQUIRED configuration of SourbyCraft's own; there is no
  SourbyCraft setting involved.
