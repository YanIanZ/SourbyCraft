# Login guards inherited from the Folia baseline

Status 2026-10-20: the baseline audit below remains relevant, and SEC-11 adds an
independent SourbyCraft admission policy in `dev.iyanz.sourbycraft.security`. Its
`connection-guard.global` and `connection-guard.per-address` settings default to LOG,
observe accepted TCP sockets and initial Login Hello starts, and are LIVE after
`/sourbycraft reload`. IPv6 uses a configurable /64 default. Loopback skips per-address
checks. With BungeeCord, Velocity or PROXY protocol configured at native listener startup,
per-address socket limits are skipped (the TCP peer is the proxy) and per-address login
limits key the forwarded player address (at Hello, or after Velocity forwarding); global
limits remain active. Proxy-policy detection and installing new hooks require restart. See
[SECURITY-GUARDS.md](SECURITY-GUARDS.md#tcp-and-login-admission-sec-11) for limits,
KICK behavior, bounded memory, proxy/NAT handling and verification limits.

The inherited behavior is in `minecraft-patches/sources` (formerly Folia/Canvas).
SourbyCraft changes use separate feature patches; these baseline patches are unchanged.

## 1. What Paper does

Paper (the pinned `paperRef`) has several guards on the login path:

| Guard | Where in Paper | Behaviour |
|---|---|---|
| Per-address handshake delay | `ServerHandshakePacketListenerImpl.beginLogin`, server connection throttle | Minimum wall-clock interval between login handshakes for a transport IP; skips loopback and Unix-domain sockets |
| Join buffering | `net.minecraft.network.Connection#tick`, `MAX_PER_TICK` = `misc.max-joins-per-tick` (`paper-global.yml`, default 5: `paper-server/src/main/java/io/papermc/paper/configuration/GlobalConfiguration.java:321`) | At most N login listeners in state `VERIFYING` are ticked per server tick; `joinAttemptsThisTick` resets each tick |
| Synchronous pre-login | `ServerLoginPacketListenerImpl`, after `AsyncPlayerPreLoginEvent` | If a `PlayerPreLoginEvent` listener is registered, the (deprecated) sync event is fired on the main thread and can disallow the login |
| Duplicate profile | `PlayerList#disconnectAllPlayersWithProfile`, login state `WAITING_FOR_DUPE_DISCONNECT` | An online player with the same profile is disconnected and the new login waits for that disconnect before it finishes |

## 2. What the region-threading baseline does instead

Verified in the patch files and in the materialized sources they produce
(`sourbycraft-server/src/minecraft/java/...`, regenerated by `applyAllPatches`).

### 2.1 Join buffering: removed, `max-joins-per-tick` re-purposed

- `minecraft-patches/sources/net/minecraft/network/Connection.java.patch` replaces Paper's gate
  with `if (true) { // Folia - region threading` (materialized `Connection.java:681`) and comments
  out the per-tick reset of `joinAttemptsThisTick` under `// Folia start - this is broken`
  (`:644-651`). `MAX_PER_TICK` is still declared (`:640`) but no longer guards anything.
  **Effect:** there is no per-tick cap on how many verifying logins proceed; each connection ticks
  on its own thread schedule.
- `.../server/network/ServerLoginPacketListenerImpl.java.patch` gates `VERIFYING` on
  `PlayerList#pushPendingJoin(name, uuid, connection)` instead (materialized `:98`); when it returns
  `false` the listener rewinds its tick counter (`--this.tick`) and retries next tick.
- `.../server/players/PlayerList.java.patch` adds `pushPendingJoin` (`// Folia start - max
  concurrent login`). It refuses a new login when the number of connections registered in
  `connectionById` that are **not yet** in the game state (`connectionById.size() - loggedInCount`)
  is `>= GlobalConfiguration.get().misc.maxJoinsPerTick`.
  **Effect:** `max-joins-per-tick` means *maximum concurrent pending logins* here, not *logins
  completed per tick* as Paper documents it. With the default 5, a sixth simultaneous login waits a
  tick and retries; once a login reaches the game listener it stops counting. The value is read on
  every attempt from the loaded Paper global configuration.

### 2.2 Synchronous `PlayerPreLoginEvent`: fired again (2026-10-22)

The baseline (`ServerLoginPacketListenerImpl.java.patch`) disabled it with
`if (false && PlayerPreLoginEvent.getHandlerList().getRegisteredListeners().length != 0)`; a plugin
listening only to the deprecated sync event got no callback. Minecraft feature 0073 (`guards/LegacyPreLogin`) fires it again as Paper does: after `AsyncPlayerPreLoginEvent`,
only when it has listeners, pre-set from the async result, its own final result decides: any result
other than `ALLOWED` refuses the login, also when the listener (or the async event it was pre-set
from) gave no kick message, which then is "You are not allowed to join this server." (review fix
2026-10-22: a denial without a message used to let the player in). It runs on
the **global tick** (Paper: the main thread) while the virtual authentication thread waits, bounded
(10 s to start, 10 s to finish); an unanswered check refuses the login with "The server could not
finish its login checks in time". One INFO line per listening plugin says so. A slow listener delays
the global tick, as it delayed Paper's main thread. Not configurable. `PlayerLoginEvent` still fires
(SourbyCraft's own `maxplayers/MaxPlayersBypass.java:69` relies on it).

### 2.3 Duplicate profile: same outcome, different mechanism

- Paper's path is disabled: `waitForDisconnection = false && playerList.disconnectAllPlayersWithProfile(profile)`
  (materialized `ServerLoginPacketListenerImpl.java:239`), and `PlayerList.java.patch` deletes the
  disconnect loop inside `disconnectAllPlayersWithProfile` (`// Folia - region threading`), so
  `WAITING_FOR_DUPE_DISCONNECT` is never entered.
- Replacement: `pushPendingJoin` keeps `connectionByName` / `connectionById` under
  `connectionsStateLock`. A conflicting name or UUID that is still connected gets
  `disconnectSafely(multiplayer.disconnect.duplicate_login)` and the new login is refused for that
  tick; it retries until `removeConnection` has dropped the old entry. The check therefore covers
  every connection from `VERIFYING` onward, not only players already in game.

## 3. What this means in practice

- **Login starts now have a separate SourbyCraft rate policy.** SEC-11 observes sockets at
  TCP initialization and valid-state initial Login Hello packets across channels. It does not
  restore Paper's per-tick completion buffering or deprecated sync pre-login callback. LOG
  counts/logs without refusing admission; KICK is an operator opt-in. There is also an inherited
  minimum-IP-interval handshake throttle (`bukkit.yml` `settings.connection-throttle`), which is
  separate from the concurrent-pending cap and these new fixed-window limits. The inherited
  throttle skips loopback and disables itself for BungeeCord/Velocity; SEC-11 skips loopback,
  never applies per-address socket limits to a proxy, and keys per-address login limits by
  the forwarded player address in all three proxy modes.
  Direct NAT users still share an address/prefix budget. Per-address KICK rejects consume
  no global allowance; LOG/OFF events and per-address bypasses still count globally.
- **`max-joins-per-tick` does not do what the Paper docs say.** Operators tuning it for a login
  burst are changing the concurrent-pending cap. Whether that cap deserves its own key is an owner
  decision; either way it would be a feature patch over the baseline.
- **Plugin authors:** prefer `AsyncPlayerPreLoginEvent` or `PlayerLoginEvent`; the sync
  `PlayerPreLoginEvent` works again (§2.2) but holds the global tick while it runs.
- Only the new `connection-guard` limits/modes are SourbyCraft-owned LIVE settings on this page.
  The baseline behaviors described in §2 retain their existing semantics.
